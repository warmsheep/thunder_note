# 闪记完整开发计划

## 文档定位
本文档是闪记项目后续开发工作的总计划文档，用于长期维护整个项目从 **MVP → 增强版 → 完整项目 → 远期扩展** 的推进路线。所有开发任务、模块边界、接口级 TODO、阶段依赖与验收口径，后续都以本文件为主维护。

本文档严格区分四类信息：
- **当前已实现**：代码中已存在并可核对
- **当前部分实现**：代码中已有骨架或局部能力，但未形成闭环
- **当前主线必补**：为了形成可用产品主线，必须尽快完成
- **目标态规划**：方向已明确，但不属于当前主线交付范围

## 计划使用规则
- 每个任务都应尽量标注：**状态**、**来源**、**依赖**、**验收出口**。
- 事实来源优先级遵循根目录 `AGENTS.md`：代码/迁移脚本 > 当前态文档 > 目标态文档 > HTML 原型。

## 一、项目目标

### 1.1 产品目标
闪记希望提供一套围绕“短笔记 + 对话消息 + 合集整理 + 多端同步”展开的个人知识记录体验。最终目标不是单一笔记应用，而是一个支持多端协同、内容沉淀、轻量沟通式记录与结构化整理的知识管理产品。

### 1.2 当前现实
当前仓库真实落地内容包括：
- Spring Boot 后端
- Android Java 客户端（当前主模块）
- HTML 原型
- 中文设计与规划文档

当前尚未落地代码的部分包括：
- Web 用户端：已进入后续计划，代码归属为 `thunder_note_server/`，但当前仍未落地真实 Web 代码
- iOS 客户端
- 管理后台
- 搜索、收藏、完整同步协议、完整多媒体消息体系

### 1.3 当前总原则
当前阶段是"在 Java 客户端已经接管主模块的前提下，继续补齐核心页面、数据链路和后端真实联调"。后端仍继续作为真实事实来源。

### 1.4 Android 客户端决策
- Android 当前 `thunder-note-android/` 为 **Java 客户端主模块**。

### 3.5 Android 聊天 / 上传 / 闪记列表数据流重构专项（新增执行主线）

> **定位**：这是面向后续新会话直接执行的专项 backlog，用于收敛 Android 当前“聊天空白、上传状态丢失、闪记列表重复请求”的系统性问题。
>
> **背景结论（2026-03-23）**：当前 Android 客户端在 `chat/message + flashnote list + upload/sync` 这条链路上，存在明显的数据流层架构缺陷：
> - 聊天消息与上传中状态仍主要依赖内存 `LiveData + HashMap`，不是稳定的本地单一事实源；
> - `MessageRepositoryImpl.bindFlashNote()/bindContact()` 先清空列表再拉远端，容易制造空白聊天；
> - `FlashNoteViewModel` 构造刷新 + `FlashNoteTabFragment.onResume()` 刷新 + `MainShellFragment` 历史上的 tab 重建策略，共同造成过闪记列表频繁请求；
> - 当前 sync/file 仍是 MVP 最小闭环，不足以支撑“离开页面后仍稳定显示上传中、回到页面继续可见”的产品预期。
>
> **执行原则**：
> 1. 先止血，再重构，再做真正离线优先；
> 2. 每一阶段都必须可独立验收，不允许跨阶段混改导致回归面失控；
> 3. 所有改动优先围绕 `thunder-note-android/` 收敛，除非后端接口契约明确不够用；
> 4. 每完成一个阶段，必须同步回写本文件与《开发测试部署经验库》。 

#### 3.5.1 当前已确认的根因清单（作为后续会话前置事实）
- `thunder-note-android/app/src/main/java/com/flashnote/java/data/repository/MessageRepositoryImpl.java`
  - 当前用 `Map<Long, MutableLiveData<List<Message>>> conversations` 承载消息主链，仍是**内存态**。
  - 历史问题：`bindFlashNote()` / `bindContact()` 曾先 `setValue(new ArrayList<>())` 再 `loadMessages()`，是“聊天空白”的第一直接根因；**2026-03-23 已完成止血修复**，当前已改为“有缓存消息则不清空，只在无缓存时首次加载”。
- `thunder-note-android/app/src/main/java/com/flashnote/java/ui/chat/ChatViewModel.java`
  - 历史问题：发送/上传链路曾依赖当前会话上下文，异步回调可能串到新聊天；**2026-03-23 已完成一轮止血修复**，当前媒体发送优先使用显式目标会话 / `Message` 自带目标字段。
- `thunder-note-android/app/src/main/java/com/flashnote/java/ui/chat/ChatFragment.java`
  - Fragment 生命周期与上传/发送回调仍有耦合，虽然已做一轮 `isAdded()` 风险收敛，但结构上仍不是后台可持续状态机。
  - 历史问题：聊天页曾使用 `Activity` 级共享 `ChatViewModel`，导致不同聊天页共享当前会话状态；**2026-03-23 已完成止血修复**，当前已改为 `Fragment` 级 `ChatViewModel` 隔离实例。
- `thunder-note-android/app/src/main/java/com/flashnote/java/ui/main/FlashNoteViewModel.java`
  - 历史问题：构造函数内自动 `refresh()` 会放大闪记列表重复请求；**2026-03-23 已完成止血修复**，当前改为 `refreshIfNeeded()`。
- `thunder-note-android/app/src/main/java/com/flashnote/java/ui/main/FlashNoteTabFragment.java`
  - 历史问题：`onResume()` 无条件 `refresh()` 会导致 idle 场景重复请求；**2026-03-23 已完成止血修复**，当前改为 `refreshIfNeeded()`。
  - 历史问题：从闪记列表悬浮 `+` 发起上传后，若立刻进入并退出收集箱，上传完成/失败回调可能因 Fragment 生命周期检查提前返回，导致本地占位消息长期停留在 `uploading=true`；**2026-03-24 已完成止血修复**，当前上传结果回写已与页面 UI 存活解耦，失败时会清理本地假占位。
- `thunder-note-android/app/src/main/java/com/flashnote/java/ui/main/MainShellFragment.java`
  - 历史上 tab 切换采用 `replace()`，会触发 Fragment 重建，放大列表刷新问题；当前已改为 `add/show/hide` 复用，但仍需继续收口 `state saved` 提交边界。
- `thunder-note-android/app/src/main/java/com/flashnote/java/data/repository/SyncRepositoryImpl.java`
  - 当前仍适合作为“调试/最小闭环同步”，不适合作为可靠离线优先执行器。
- `thunder-note-android/app/src/main/java/com/flashnote/java/data/repository/PendingMessageDispatcher.java`
  - 2026-03-28 新确认根因：失败分支曾在 `fail(...)` 里立即再次 `dispatchAllPendingNow()`，且 `STATUS_FAILED` 仍被视为可派发状态，导致离线时会出现“失败 → 立刻重发 → 再失败”的高速自旋重试风暴。
  - **2026-03-28 已完成止血修复**：当前失败分支仅落库为 `FAILED` 并释放 `dispatchInProgress`，不再在同一次失败回调里立刻扫全队列；后续重试交由显式入口（聊天重进、手动重试、恢复链路）触发。
- `thunder-note-android/app/src/main/java/com/flashnote/java/data/repository/PendingMessageRepositoryImpl.java`
  - 2026-03-28 新确认根因：`PROCESSING / UPLOADING / UPLOADED / SENDING` 会被计入待同步列表，但 dispatcher 只会派发 `QUEUED / FAILED`，导致 APP 被杀后中间态记录永久滞留，出现“聊天里已发成功、待同步列表永不消失”的状态漂移。
  - **2026-03-28 当前结论**：冷启动恢复方案已验证会引入启动/登录回归，当前未采用；待同步列表刷新已通过 `PendingSyncAdapter` 深拷贝 + `payloadJson` 差异比较收口，消息重发仍以聊天页/统一 pending 派发链为准。
- `thunder-note-android/app/src/main/java/com/flashnote/java/ui/settings/PendingSyncAdapter.java`
  - 2026-03-28 新确认根因：pending 列表如果直接复用 Room 返回的同一批 `PendingMessage` 引用，dispatcher 原地改状态时 `DiffUtil` 会把“旧值”和“新值”都看成同一个对象，导致状态变化和卡片 payload 变化不刷新。
  - **2026-03-28 已完成止血修复**：adapter 当前提交列表前会复制 `PendingMessage`，并把 `payloadJson` 纳入内容比较，待同步列表能正确反映状态与卡片内容变化。
- `thunder-note-android/app/src/main/java/com/flashnote/java/data/repository/SyncRepositoryImpl.java`
  - 2026-03-28 新确认根因：手动同步曾保留一套独立的 `messages` 批量 push 逻辑，与聊天页使用的 `PendingMessageDispatcher` 发送链并行，导致“进入聊天页能成功、点同步按钮却报 SQL 唯一冲突/卡片变未知内容”的双轨行为。
  - **2026-03-28 已完成止血修复**：手动同步当前先调用 `messageRepository.retryAllPendingMessages()`，复用聊天页同一条 pending 发送链；`syncAll()` 构建的 push payload 不再包含 `messages`，同时兼容 pull 响应中的 `payload` / `payloadJson`，避免卡片 payload 丢失。

### 3.5.4 P1：结构收敛（建立本地 pending / outbox 主链）

#### P1 目标
- 让“上传中/待发送”消息有稳定的本地状态来源，而不是仅依赖内存对象。
- 聊天页展示改为“远端消息 + 本地 pending/outbox 合并视图”。
- 即便离开页面，回来后仍能从本地恢复看到待上传/待发送项。

#### P1 实施边界（必须先统一认知）
- P1 **不是**“真正离线优先”，也**不是**“APP 杀进程后自动后台恢复上传/发送”；这些属于 P2。
- P1 只收口“未确认消息”这条链：
  - 已确认消息：继续沿用当前 `MessageRepositoryImpl` 的远端拉取 + 当前分页 + 当前会话缓存。
  - 未确认消息：新增一个最小本地 pending/outbox 事实源。
- P1 不做大爆炸重写，必须保持以下部分尽量不动：
  - `MessageRepositoryImpl` 的远端分页主链；
  - `ChatFragment` 的页面结构与基础交互；
  - `MessageAdapter` 的主体渲染结构；
  - 闪记列表与收藏/合集等非聊天主链页面。

#### P1 关键约束（实施红线）
- 一条用户发送意图只允许对应一条本地 pending 记录，所有上传/发送/失败/重试都按 `localId` 归位。
- 任何网络动作开始前，pending 记录必须已经落本地；否则切页/重建后无法恢复。
- Dispatcher 只能读取 pending 行内的 `flashNoteId / peerUserId / conversationKey`，不能依赖“当前打开的聊天页”。
- 远端 confirmed 消息与本地 pending/outbox 必须分源存储，不能继续把 pending 直接混写进远端 `conversations` 缓存源。
- UI 最终只能观察“远端 confirmed + 本地 pending”的合并结果；Fragment 不再直接维护发送状态机。

#### P1 推荐实施顺序（已完成，仅保留归档结论）
1. 文本消息先行进入 pending/outbox。
2. 合并展示层收口为 confirmed + pending 双源模型。
3. 建立最小 outbox 执行器。
4. 媒体链路接入 upload -> send 状态机。
5. 失败恢复、单条重试与最小回归矩阵补齐。

> 注：原 P1-0 准备阶段中的 Room、pending store、会话 key、DAO/Repository 基础设施均已在后续实现中落地，旧未勾选前置清单已删除，避免与“P1 已完成”的当前事实冲突。

### 3.5.7 Android 代码审查整改专项（新增执行主线）

> **定位**：这是基于 2026-03-26 对 `thunder-note-android/` 的系统性代码审查新增的整改 backlog，重点收敛当前 Android Java 客户端在**安全、异常处理、生命周期稳定性、性能、硬编码、代码冗余与可维护性**上的问题。
>
> **与 3.5 数据流专项的关系**：
> - 3.5.3 ~ 3.5.6 主要解决“聊天空白 / 上传状态丢失 / 列表重复请求”这类主链数据流问题；
> - 本节 3.5.7 主要解决“已经接通主链后，代码质量和工程风险仍偏高”的问题；
> - 两者不是替代关系。凡是涉及聊天 / 闪记列表 / pending/outbox 的整改，必须先判断它属于**主链数据流修复**还是**代码治理整改**，禁止混成一次大爆炸重构。
>
> **背景结论（2026-03-26 审查）**：当前 Android 客户端已不是简单壳层，而是真实主链 + 过渡性架构并存的状态，主要问题集中在：
> - 安全边界仍有明显缺口：refresh token 仍出现在 URL query，debug 网络日志仍可能暴露敏感信息；
> - 多处异常处理仍偏“吞异常 / printStackTrace / 直接 RuntimeException”，不利于线上稳定性和排障；
> - 主壳虽已改为 `add/show/hide` 复用，但 `state-saved` 提交、低频页面生命周期边界，以及大 Fragment / 大 Adapter / 大 Repository 仍持续放大回归风险；
> - 文案、版本号、提示词、状态文案仍有较多硬编码，资源治理不一致；
> - repository / ViewModel / adapter 层存在明显模板化重复，后续维护成本偏高。
>
> **执行原则**：
> 1. 先收敛安全与崩溃风险，再收敛生命周期与列表稳定性，再做结构化重构；
> 2. 每个子阶段都必须可独立回归，不允许“顺手重写整个聊天页 / 主壳 / 全部 repository”；
> 3. 当前阶段优先修**活跃路径**与**高频路径**，不要先清理低频美化代码；
> 4. 凡是整改涉及现有行为变化，必须补最小验证项；
> 5. 凡是整改沉淀出可复用规则，完成后再回写《开发测试部署经验库》。

## 四、当前已确认冲突与前置修复项

本节只保留**当前仍会影响后续开发判断**的冲突与边界；历史上已经收口的问题不再继续写成“当前未解决”。

### 4.1 路径冲突
- 历史文档曾大量使用 `/api/v1/...`，当前真实后端路径为 `/api/...`。
- Android 当前主链接口声明已基本收口到真实路径；后续若新增/修改 API，仍必须先核对 controller，再更新 Android 声明与文档。

### 4.2 登录语义冲突
- 历史上文档与部分旧实现曾按邮箱登录描述；当前真实后端登录字段是 `username`，Android 当前主链也已按该语义收口。
- 后续若再改认证相关文案、DTO 或接口声明，必须继续保持“用户名登录”这一当前事实，不要回写成邮箱语义。

### 4.3 模型冲突
- 历史上 Android 本地模型与后端字段存在明显漂移；当前主链已完成一轮收口，但“本地展示模型 ≠ 后端表结构”仍是常态，需要显式区分。
- 当前仍需持续注意两类边界：
  - 闪记：后端真实主字段以 `title / content / tags / is_deleted` 为准，Android 的 `pinned / hidden / inbox / icon` 等展示/扩展能力不能反推为后端基础表结构已经完全同构。
  - 消息：Android 当前展示模型已经覆盖 `flashNoteId / role / media / favorite / payload` 等扩展语义，但后端真实契约应以当前 controller + DTO + 数据库实现为准，不能只看 UI 字段名推断。

### 4.4 同步冲突
- 后端有 `bootstrap / pull / push` 基础接口
- Android `SyncRepositoryImpl` 已接最小真实链路，但仍未形成完整离线同步体系
- 后端 `push` 已能处理 notes / collections / messages / favorites，仍缺冲突解决与删除回放

### 4.5 功能面冲突
- Android 已有 Favorite / Collection / Profile 等真实页面与主链，不应再按“页面壳层/演示页”判断当前成熟度。
- 当前真正仍需区分的是：
  - Favorite 已完成消息收藏最小闭环，但更复杂收藏模型仍未进入当前阶段；
  - Profile 已接真实资料、同步、头像、设置入口；设置页当前还可查看 pending/outbox 的待同步消息列表，但整体仍偏“操作台式页面”；
  - sync / 离线 / 恢复链仍是“最小闭环 + 后续收口”，不是完整终态。

## 八、阶段 D：远期扩展

## D1. Web 用户端

### D1.1 定位与当前事实
- **定位**：Web 版是面向桌面浏览器与移动浏览器的闪记用户端，不是管理后台。
- **代码归属**：按当前决策，Web 版代码写入 `thunder_note_server/`；同一个 Spring Boot 服务继续向 Android 提供 `/api/...`，同时托管 Web 页面。
- **当前事实**：`thunder_note_server/` 当前是纯 Spring Boot API 服务，`src/main/resources/` 下只有配置与 Flyway 迁移，尚无 Web 静态资源、模板页面或前端构建链。
- **接口事实**：Web v1 必须优先复用当前 controller 的真实路径与响应结构，不引入 `/api/v1/...`，登录字段继续使用 `username`。
- **安全事实**：当前 `SecurityConfig` 除 `/api/auth/login`、`/api/auth/register`、`/api/auth/refresh`、`/actuator/health` 外均要求认证；后续 Web 静态资源、前端路由 fallback、文件下载与 API 鉴权边界必须单独设计，不能直接把 `anyRequest().authenticated()` 改成全量放行。

### D1.2 Web v1 范围
- [ ] 登录 / 注册 / token 刷新 / 登出
- [ ] 闪记列表：展示收集箱、普通闪记、图标、最新消息、置顶/隐藏状态
- [ ] 闪记管理：创建、编辑、删除、置顶/取消置顶、隐藏/取消隐藏
- [ ] 闪记会话：按 `flashNoteId` 拉取消息、发送文本消息、删除消息、支持收集箱 `flashNoteId=-1`
- [ ] 合集目录：读取合集列表，按 `flash_notes.tags` 组织“合集 - 闪记”层级
- [ ] 收藏：展示已收藏消息、取消收藏、从消息操作中加入收藏
- [ ] 文件基础：上传文件并发送媒体消息，按 `GET /api/files/download?objectName=...` 预览或下载
- [ ] 搜索基础：复用 `/api/flash-notes/search` 做闪记与消息搜索
- [ ] 个人资料：读取/编辑 `/api/users/profile`，支持头像 URL 或文件上传后的头像回写

### D1.3 暂不纳入 Web v1 的范围
- [ ] 不做 iOS、管理后台或多租户后台能力
- [ ] 不做完整离线优先、冲突解决与复杂同步编辑器
- [ ] 不做独立 WebSocket 新协议；如需实时能力，优先评估复用当前 `GET /api/messages/stream` SSE
- [ ] 不重写后端核心数据模型；Web 首版以现有 `auth / flashnote / message / collection / favorite / file / sync` 契约为准
- [ ] 不把 Android 本地手势锁照搬成 Web 登录方式；Web 只沿用用户名密码 + JWT 登录态

### D1.6 Web v1 范围之外（明确不跟进）
> 这些是 Android 当前已实现，但因 Web 上下文限制或投入产出比，**不在 Web v1 范围内**；如要补齐应作为单独阶段（v2）评估，避免后续会话误判。
- 手势锁（GestureLock 整套）：移动端离屏锁屏特性，Web 由 sessionStorage + token TTL 保障即可
- 系统分享接收（ShareReceiverActivity）：Android Intent 系统集成，Web 无对应概念
- 离线同步引擎（`/api/sync/bootstrap|pull|push` + Room + PendingMessage + PendingRecoveryWorker）：Web 上需 IndexedDB + Service Worker，重投入；Web v1 默认在线
- 录音 / 语音消息（ChatRecordingHelper / VoiceWaveView）：浏览器 MediaRecorder 体验差，Web v1 不做
- 视频压缩（VideoCompressor）：浏览器内压缩需 wasm，重投入
- 服务端 BaseURL 配置（ServerSettingsFragment）：Web SPA 跟着 origin 走，无需切换
- 调试日志查看页（DebugLogViewerFragment）：Web 由浏览器 DevTools 提供等价能力
- 全局快速捕获（QuickCaptureTextFragment）：Android 系统级捷径，Web 无系统集成；如需可在 v2 提供"悬浮快记"入口

## 十、前置依赖与顺序约束

### 必须优先完成
1. 文档/路径/字段统一
2. Android 认证打通
3. FlashNote 与 Sync API 对齐

### 依赖关系
- 没有真实登录态，就不应继续推进 Android 主线联调
- 没有统一的闪记/消息模型，就不应先做复杂同步
- 没有 FileApi / CollectionApi，就不应把多媒体与合集体验当成已完成
- 没有 MVP 同步闭环，就不应直接推进完整冲突系统
- 没有最小测试与回归检查，就不应把增强版能力视为稳定可交付
- 没有冻结 Web 静态资源路由与 Spring Security 边界，就不应把 Web 页面直接接入生产服务，避免误放行 `/api/**` 或破坏 Android 既有调用

### 优先级取舍规则
- 如果多个任务同时可做，优先处理会阻塞后续阶段的任务。
- 如果一个任务属于目标态，但当前主线仍未闭环，默认优先当前主线。
- 如果一个任务只是优化体验，但存在路径/模型/接口漂移，默认先修漂移。
