# 闪记完整开发计划

## 文档定位
本文档是闪记项目后续开发工作的总计划文档，用于长期维护整个项目从 **MVP → 增强版 → 完整项目 → 远期扩展** 的推进路线。所有开发任务、模块边界、接口级 TODO、阶段依赖与验收口径，后续都以本文件为主维护。

本文档严格区分四类信息：
- **当前已实现**：代码中已存在并可核对
- **当前部分实现**：代码中已有骨架或局部能力，但未形成闭环
- **当前主线必补**：为了形成可用产品主线，必须尽快完成
- **目标态规划**：方向已明确，但不属于当前主线交付范围

## 计划使用规则
- 每个任务都应尽量标注：**状态**、**来源**、**依赖**、**验收出口**。
- 事实来源优先级遵循根目录 `AGENTS.md`：代码/迁移脚本 > 当前态文档 > 目标态文档 > HTML 原型。
- 如果某条 TODO 会影响接口、数据结构、跨端行为，必须先补充“当前事实”再推进开发。
- 当前主线只围绕 **Spring Boot 后端 + Android 客户端**，Web / iOS / admin 一律放到远期阶段。
- 本文档是唯一执行型 backlog；`TODO事项.md` 只作为路线图摘要，不再与本文件并行维护详细执行优先级。

## 一、项目目标

### 1.1 产品目标
闪记希望提供一套围绕“短笔记 + 对话消息 + 合集整理 + 多端同步”展开的个人知识记录体验。最终目标不是单一笔记应用，而是一个支持多端协同、内容沉淀、轻量沟通式记录与结构化整理的知识管理产品。

### 1.2 当前现实
当前仓库真实落地内容包括：
- Spring Boot 后端
- Android Java 客户端（当前主模块）
- HTML 原型
- 中文设计与规划文档

当前尚未落地代码的部分包括：
- Web 用户端
- iOS 客户端
- 管理后台
- 搜索、收藏、完整同步协议、完整多媒体消息体系

### 1.3 当前总原则
当前阶段是"在 Java 客户端已经接管主模块的前提下，继续补齐核心页面、数据链路和后端真实联调"。后端仍继续作为真实事实来源。

### 1.4 Android 客户端决策
- Android 当前 `thunder-note-android/` 为 **Java 客户端主模块**。

## 四、当前已确认冲突与前置修复项

这些事项不解决，后续开发会持续返工，必须优先纳入计划。

### 4.1 路径冲突
- 文档历史路径：`/api/v1/...`
- 当前真实后端路径：`/api/...`
- Android 远程 API 声明仍存在路径漂移，例如：
  - `FlashNoteApi` 使用 `flashnotes`
  - 后端真实是 `flash-notes`

### 4.2 登录语义冲突
- 当前后端登录字段：`username`
- Android `AuthViewModel` / `AuthRepositoryImpl` 仍按邮箱语义处理

### 4.3 模型冲突
- 后端 `flash_notes`：`title / content / tags / is_deleted`
- Android 闪记：`summary / pinned / hidden / syncStatus`
- 后端 `messages`：`sender_id / receiver_id / content / read_status`
- Android 消息：`flashNoteId / role / imageUrl / favorited`

### 4.4 同步冲突
- 后端有 `bootstrap / pull / push` 基础接口
- Android `SyncRepositoryImpl` 已接最小真实链路，但仍未形成完整离线同步体系
- 后端 `push` 已能处理 notes / collections / messages / favorites，仍缺冲突解决与删除回放

### 4.5 功能面冲突
- Android 已有 Favorite / Collection / Profile 等展示面
- Favorite 已完成消息收藏的最小后端支持；更复杂收藏模型仍未进入当前阶段
- Android 部分页面仍是演示数据，不是实际业务流

## 十、前置依赖与顺序约束

### 必须优先完成
1. 文档/路径/字段统一
2. Android 认证打通
3. FlashNote 与 Sync API 对齐

### 依赖关系
- 没有真实登录态，就不应继续推进 Android 主线联调
- 没有统一的闪记/消息模型，就不应先做复杂同步
- 没有 FileApi / CollectionApi，就不应把多媒体与合集体验当成已完成
- 没有 MVP 同步闭环，就不应直接推进完整冲突系统
- 没有最小测试与回归检查，就不应把增强版能力视为稳定可交付

### 优先级取舍规则
- 如果多个任务同时可做，优先处理会阻塞后续阶段的任务。
- 如果一个任务属于目标态，但当前主线仍未闭环，默认优先当前主线。
- 如果一个任务只是优化体验，但存在路径/模型/接口漂移，默认先修漂移。
