# 开发测试部署经验库

## 文档定位
本文档用于沉淀在开发、联调、测试、构建、部署过程中遇到的真实问题、根因、解决方式和后续规则。它不是设计文档，而是为了避免后续新会话重复踩同样的坑。

## 使用规则
- 新会话开始处理开发、联调、测试、构建、部署类任务前，先快速浏览本文件。
- 只有**真实遇到过的问题**才写入本文件，不记录纯设想。
- 每条经验尽量写清：现象、根因、解决方式、后续规则。
- 如果某条经验已经被固化进代码或流程，也保留简短记录，避免后续再次误判。

## 已沉淀经验

### 1. Android 与后端接口声明不能直接互信
**现象**
- Android API 声明存在，但联调时仍出现 404、方法不匹配、字段不匹配。

**根因**
- Android `FlashNoteApi`、`MessageApi`、`SyncApi` 与后端 controller 曾长期漂移。

**解决方式**
- 联调前先核对 `docs/当前联调契约总表.md`。
- 真实联调时，以后端 controller 和 DTO 为最终事实来源。

**后续规则**
- Android API、DTO、repository 变更后，必须同步核对后端 controller/DTO。

### 2. 页面存在不等于业务已接通
**现象**
- Android 有页面、有 ViewModel，但实际仍是假数据或 mock/stub 实现。

**根因**
- 历史上 `CollectionViewModel`、`FavoriteViewModel` 曾存在骨架或演示数据；当前应先按代码核对其 repository / Room / 本地观察链是否已接入真实实现，不再直接沿用旧印象判断。

**解决方式**
- 判断模块完成度时，不看页面是否存在，而看 repository 是否真实接入、ViewModel 是否仍依赖假数据。

**后续规则**
- 后续会话评估"已实现/部分实现"时，优先核对 repository、API、DTO、真实返回值。

### 3. sync 相关描述最容易误导
**现象**
- 文档里容易把"已有 bootstrap/pull/push 接口"误写成"同步已实现"。

**根因**
- 当前后端 sync 虽已具备最小可用闭环，Android `SyncRepositoryImpl` 也已进入真实主链，但它仍不等于“完整离线同步协议已经实现”。

**解决方式**
- 统一把 sync 描述为“最小闭环 / 部分实现”，除非已经具备完整协议、冲突解决与恢复语义。

**后续规则**
- 以后凡是提到 sync，都要区分：接口存在、最小闭环、完整协议 三个层级。

### 4. 文档修正后仍要继续回写经验
**现象**
- 即使主计划、API、数据库、客户端文档已经清理过，后续开发中仍可能遇到新坑。

**根因**
- 经验型问题不会天然出现在设计文档里。

**解决方式**
- 发生一次真实问题后，优先把稳定经验沉淀到本文件，再决定是否同步回写到设计文档或 AGENTS。

**后续规则**
- 开发、测试、部署过程中遇到的重复性问题，应优先进入本文件。

### 5. `mvn test` 通过不只取决于业务代码
**现象**
- 本次完成 MVP 主链改动前，`mvn clean compile` 成功，但 `mvn test` 中现有 `ControllerHttpMethodContractTest` 直接出现多个 controller `NoClassDefFoundError`。

**根因**
- 当前后端测试基线本身存在类加载/测试装配问题，失败点不是业务断言，而是测试运行期无法加载 controller 类。

**解决方式**
- 先用 `mvn clean compile` 区分“主代码可编译”与“测试基线完整可运行”。
- 将这类 controller 契约测试改成直接读取源码片段校验注解声明，避免因运行时类加载装配导致误报。

**后续规则**
- 后续会话遇到后端测试失败时，先判断是业务断言失败还是测试装配失败，避免把两类问题混为一谈。

### 6. Mockito inline mock maker 在当前后端测试环境下不稳定
**现象**
- 新增后端行为测试时，Mockito 在当前环境下对接口做 inline mock 会触发 `Byte Buddy` / `NoClassDefFoundError` 类问题，导致测试失败点落在 mock 基线而不是业务断言。

**根因**
- 当前 JDK + surefire + Mockito inline 组合在这个仓库里不够稳定，动态字节码重写会放大类加载问题。

**解决方式**
- 在 `thunder-note-server/src/test/resources/mockito-extensions/org.mockito.plugins.MockMaker` 中切到 `mock-maker-subclass`，让后端行为测试回到稳定基线。

**后续规则**
- 后续如果继续补后端单测，优先沿用 subclass mock maker，不要默认回到 inline mock maker。

### 7. 根仓与 Android/Server 子仓库不能混着提交
**现象**
- 本次改动中，根仓 `.gitignore` 虽然已忽略 `thunder-note-server/`、`thunder-note-android/`，但如果在根仓使用 `git add -f`，仍会把子仓代码快照错误纳入根仓提交。

**根因**
- 当前项目是“根仓 + 两个独立子仓库”的协作结构；根仓用于文档、原型、脚本与规则，后端和 Android 各自维护自己的 git 历史。

**解决方式**
- 提交前先判断变更归属。
- `thunder-note-server/` 改动进入后端子仓提交；`thunder-note-android/` 改动进入 Android 子仓提交；根仓只提交文档/原型/规则类改动。
- 如果误在根仓纳入子仓代码，使用 `git rm --cached` 从根仓索引移除，再到对应子仓重新提交。

**后续规则**
- 后续涉及 git 提交时，必须先确认当前所在仓库与变更归属，禁止在根仓用 `git add -f` 强行纳入子仓代码。

### 8. 本地 5432 已有 PostgreSQL 时，不要直接改现有实例
**现象**
- 本次重新部署后端时，`application.yml` 默认连接 `localhost:5432`，但本机已有 PostgreSQL 在运行，且 `postgres/postgres` 认证不匹配，导致 Spring Boot 在 Flyway 初始化阶段直接报 `password authentication failed for user "postgres"`。

**根因**
- 项目默认本地配置假设了一套独立测试库，但实际机器上的 `5432` 可能被其他 PostgreSQL 实例占用，账号密码也未必与仓库默认值一致。

**解决方式**
- 不直接修改现有 `5432` 实例，改为单独启动一个测试用 PostgreSQL 容器，例如映射到 `15432`。
- 启动后端时通过运行参数覆盖数据源：`--spring.datasource.url=jdbc:postgresql://localhost:15432/thunder_note --spring.datasource.username=postgres --spring.datasource.password=postgres`。

**后续规则**
- 后续本地重启后端前，若发现 `5432` 已被占用，优先起独立测试库并用启动参数覆盖，不要默认接管现有数据库实例。

### 9. Android Debug 包的接口基址必须和当前本地服务一致
**现象**
- 本次联调里，后端在 `192.168.3.7:8080` 正常提供登录、资料、闪记、合集接口，但 Android debug 包仍指向旧的 `192.168.3.7:8081`，导致登录后的资料、闪记、合集看起来“为空”或命中错误服务。

**根因**
- `thunder-note-android/app/build.gradle.kts` 里的 debug `BASE_URL` 没有随当前本地服务端口一起更新。

**解决方式**
- 将 Android debug `BASE_URL` 对齐到当前实际联调地址：`http://192.168.3.7:8080/`。

**后续规则**
- 每次重新部署本地后端并给测试包前，必须先核对 Android debug `BASE_URL` 与当前实际联调地址是否一致。

### 10. 用户资料接口必须走 `/api/users/profile`
**现象**
- Android “我的”页会报 `获取资料失败：No static resource users/profile`。

**根因**
- Android `UserService` 把资料接口写成了 `users/profile`，漏掉了后端当前真实前缀 `/api`。

**解决方式**
- 将 Android `UserService` 中的资料获取/更新路径统一改为 `/api/users/profile`。

**后续规则**
- Android 新增或修改接口时，必须先以 controller 的真实 `@RequestMapping` + `@PostMapping/@PutMapping` 为准，不要手写省略版路径。

### 11. 登录成功后先落 token 再进主壳，避免首登列表空
**现象**
- 首次安装后登录成功进入主壳，闪记/合集列表可能为空；但随后新建闪记、发消息又能成功。

**根因**
- 登录页先根据 `authState=SUCCESS` 导航到主壳，再在另一个 observer 里异步写 token（`SharedPreferences.apply()`）。
- 主壳初始化时仓库立即请求列表，请求可能发生在 token 落盘前，导致无鉴权请求返回空/失败。

**解决方式**
- 登录页改为在 `loginResponse` 回调里先保存 token，再导航到主壳。
- `TokenManager.saveTokens/saveAccessToken` 改为 `commit()`，确保写入同步完成。

**后续规则**
- 任何“登录后立即发起鉴权请求”的流程，都必须保证 token 已可读再导航或再触发首轮刷新。

### 11.1 Android 首装/重装后冷启动时，不能在 Application 中提前初始化依赖当前用户的会话仓储
**现象**
- 卸载 App 后重新安装，第一次打开应用会在 Splash 前后直接闪退，连登录页都进不去。
- 日志堆栈落在 `RepositoryAuthSupport.requireCurrentUserId()`，异常为 `IllegalStateException: User not logged in`。

**根因**
- `FlashNoteApp.initializeDependencies()` 旧实现会在 `Application.onCreate()` 阶段直接创建 `FlashNoteRepositoryImpl`、`CollectionRepositoryImpl`、`FavoriteRepositoryImpl` 和 `SyncRepositoryImpl`。
- 其中前三个 repository 在构造函数里就会读取 `TokenManager.getUserId()` 绑定当前用户的 Room 观察键；首装/重装后的首次启动还没有登录态，`userId` 为空，于是直接在应用启动阶段抛异常。
- 同时，登录/注册成功后会立刻调用 `reloadSessionScopedDependencies()`；如果这个方法重建整套基础依赖，或 `saveUserId/saveUsername` 仍用异步 `apply()`，就会在“刚写入 userId → 立即重载会话依赖”的窗口里再次读不到当前用户身份。

**解决方式**
- 将 `FlashNoteApp` 依赖装配拆成两层：登录前只初始化 `TokenManager`、`ApiClient`、Room、`AuthRepository`、`MessageRepository`、`UserRepository` 等安全基础依赖；`FlashNoteRepository`、`CollectionRepository`、`FavoriteRepository`、`SyncRepository` 改为仅在 `userId` 已存在时初始化。
- `reloadSessionScopedDependencies()` 只重载会话级依赖，不再重建整套 Application 基础设施。
- `TokenManager.saveUserId/saveUsername` 改为 `commit()`，保证“登录成功后立刻重建会话依赖”时能同步读到当前用户身份。
- 已补充 `FlashNoteAppTest` 回归测试，覆盖“未登录冷启动不崩”和“保存 userId 后会话依赖可立即恢复”两条路径。

**后续规则**
- 任何依赖“当前用户身份”的本地仓储、观察器或同步组件，都不能在 `Application.onCreate()` 中无条件创建；要么延迟到登录后初始化，要么在无用户态时明确返回空实现/空状态。
- `reloadSessionScopedDependencies()` 这类方法只应用于重建会话态依赖，不要顺手重建 `TokenManager`、网络层、数据库等基础设施，避免把刚写入的登录态又置于新的时序窗口里。
- 只要后续流程存在“写入身份信息后立即读取”的场景，优先使用同步持久化，避免 `apply()` 带来的瞬时不可见问题。

### 12. Fragment 导航与异步回调统一做生命周期安全处理
**现象**
- 退出登录、底部 tab 切换、聊天返回等场景反复出现 `IllegalStateException`。

**根因**
- 在 Fragment/Activity 状态已保存或 Fragment 已脱附后仍执行事务提交或 `requireActivity()/requireContext()`。

**解决方式**
- 根导航与子导航在 `isStateSaved` 场景使用 `commitAllowingStateLoss()`；清理 back stack 时避开 state saved 场景的 immediate pop。
- 异步回调里统一使用 `getActivity()/getContext()` 判空后再 UI 更新，避免 `require*` 触发异常。

**后续规则**
- 涉及 Fragment 事务或异步 UI 回调的改动，必须先过一遍"state saved + detached"场景检查。

### 13. Gson 默认不支持 java.time.LocalDateTime
**现象**
- Android 闪记/合集列表加载时报 `IllegalStateException: Expected BEGIN_OBJECT but was STRING`。

**根因**
- Android 模型（`FlashNote`、`Collection`）使用了 `java.time.LocalDateTime` 字段。
- 服务端 Jackson 将 `createdAt`/`updatedAt` 序列化为 ISO 格式字符串 `"2026-03-16T08:19:24"`。
- Gson 默认没有 `LocalDateTime` 的 TypeAdapter，尝试将字符串反序列化为对象失败。

**解决方式**
- 在 `ApiClient.java` 中为 Gson 注册 `LocalDateTimeAdapter`，使用 `DateTimeFormatter.ISO_LOCAL_DATE_TIME` 进行双向转换。

**后续规则**
- Android 模型使用 `java.time.*` 类型时，必须在 Gson 配置中注册对应的 TypeAdapter。

### 14. LiveData postValue 顺序影响 observer 中的同步检查
**现象**
- 登录成功后不跳转到主页面，但重启 APP 后直接进入主页面。

**根因**
- `AuthViewModel.login()` 回调中 `loginResponse.postValue()` 在 `authState.postValue(SUCCESS)` 之前执行。
- `handleLoginResponse()` 中添加了 `authState.getValue() == SUCCESS` 的同步检查。
- `postValue` 是异步的，当 `loginResponse` observer 触发时，`getValue()` 返回的仍是旧值（LOADING），导航被跳过。

**解决方式**
- 调换 postValue 顺序，确保 `authState.postValue(SUCCESS)` 先于 `loginResponse.postValue()`。
- 移除不可靠的同步 `getValue()` 检查。

**后续规则**
- 多个 LiveData 联动时，若 observer 中依赖另一个 LiveData 的当前值，必须考虑 postValue 的异步特性。
- 优先使用单一 LiveData 驱动 UI 状态，避免跨 LiveData 同步检查。

### 15. 调试日志功能用于捕获完整异常堆栈
**现象**
- Android Toast 显示异常信息被截断，无法看到完整堆栈。

**根因**
- Toast 长度有限，异常堆栈信息过长时被截断。

**解决方式**
- 新增 `DebugLog` 工具类，注册全局 `UncaughtExceptionHandler`。
- Repository 的 `onFailure` 回调中调用 `DebugLog.e()` 记录完整异常。
- 「我的」页面底部添加调试日志面板，可滚动查看、复制、清空日志。

**后续规则**
- 后续遇到难以定位的异常时，优先查看调试日志面板获取完整堆栈。
- 调试日志能力可以保留，但用户可见入口优先放到设置页或独立日志页，不要长期把调试面板挂在“我的”页主流程里。

### 15.1 文件上传如果统一发 `application/octet-stream`，会被服务端 MIME 白名单整体拦截
**现象**
- Android 端上传图片/语音/视频时，用户侧统一看到 `File upload failed`，看起来像所有媒体类型都坏了。

**根因**
- Android `FileRepositoryImpl.upload()` 曾把所有文件都用 `application/octet-stream` 作为 multipart part 的 content-type 发给后端。
- 后端 `FileServiceImpl` 已启用 MIME 白名单，只允许 `image/jpeg/png/gif/webp`、`video/mp4`、`audio/mpeg/mp4`、`application/pdf`。
- 同时，后端 `upload()` 曾用 `catch (Exception)` 把 `BusinessException` 一起吞掉，并统一改写成 `File upload failed`，导致客户端看不到真实原因。

**解决方式**
- Android `FileRepositoryImpl` 改为优先按扩展名显式映射 MIME（jpg/jpeg/png/gif/webp/mp4/mp3/m4a/pdf），再回退 `MimeTypeMap`，最后才回退 `application/octet-stream`。
- 后端 `FileServiceImpl.upload()` 对 `BusinessException` 原样抛出；其它异常记录 `username/fileName/contentType/size` 和完整堆栈后，再包装成 `File upload failed`。
- 已通过真实 `curl -F "file=@...;type=image/png"` 手工验证 PNG 上传成功。

**后续规则**
- Android 上传二进制文件时，不能偷懒统一使用 `application/octet-stream`，必须优先传真实 MIME。
- 后端统一异常包装前，必须先判断是否为业务异常；对底层异常必须打可定位日志，不能只返回一个泛化错误。

### 15.2 上传能力扩容时，程序内上限、Spring multipart 限制、Tomcat 限制和全局异常映射必须一起改
**现象**
- 用户要求支持 `application/octet-stream`、常见办公/代码/压缩/程序文件，并把上传上限从 10MB 提升到 200MB。
- 若只改业务代码里的 `MAX_FILE_SIZE`，超限文件仍可能在进入 controller 前就被 Spring/Tomcat 拦截，并落到全局 500。

**根因**
- 上传链路有 3 层限制：业务层 `FileServiceImpl.MAX_FILE_SIZE`、`spring.servlet.multipart.*`、Tomcat connector 限制。
- `MaxUploadSizeExceededException` 若没有单独映射，会被 `GlobalExceptionHandler.handleException(Exception)` 吞成 `Internal server error`。

**解决方式**
- 业务层将 `MAX_FILE_SIZE` 提升至 `200MB`。
- `application.yml` 同步改为：`spring.servlet.multipart.max-file-size=200MB`、`max-request-size=200MB`，并增加 `tomcat.max-http-form-post-size=209715200`、`tomcat.max-swallow-size=209715200`。
- `GlobalExceptionHandler` 增加 `@ExceptionHandler(MaxUploadSizeExceededException.class)`，统一返回 `400 + File size exceeds 200MB limit`。
- 上传白名单升级为“允许常见 MIME + 对 `application/octet-stream` 按安全后缀白名单放行”，已手工验证 `.md`、`.apk` 成功，201MB 文件明确返回 400。

**后续规则**
- 任何上传上限调整，都必须同时检查：业务校验、Spring multipart、Tomcat、全局异常映射四个层面。
- 支持 `application/octet-stream` 时，不能直接等于“放开所有文件”，应配合明确的后缀白名单控制范围。

### 16. Android Application 手动 DI 的装配顺序错误会直接导致 repository 运行期 NPE
**现象**
- 点击“我的”页面同步按钮后立即闪退，日志显示：`java.lang.NullPointerException: Attempt to invoke interface method 'void ...FavoriteRepository.refresh()' on a null object reference`。

**根因**
- `FlashNoteApp.initializeDependencies()` 中先创建了 `SyncRepositoryImpl`，再创建 `FavoriteRepositoryImpl`。
- `SyncRepositoryImpl.pullAndRefreshLocal()` 会直接调用 `favoriteRepository.refresh()`；由于构造时注入的是尚未初始化的 `favoriteRepository`，点击同步即触发运行期 NPE。

**解决方式**
- 调整 `FlashNoteApp` 中 repository 装配顺序，先初始化 `favoriteRepository`，再创建 `syncRepository`。

**后续规则**
- Application 层手动 DI 时，凡是 repository 之间存在直接调用关系，必须先创建依赖方，再创建调用方；不要默认“字段声明顺序 == 可安全注入顺序”。

### 17. 调试日志如果把持久化文件和当前内存会话直接拼接展示，会在“历史日志/当前会话”中重复出现
**现象**
- 设置页里的调试日志查看页，会把同一批日志同时显示在“历史日志”和“当前会话日志”里，看起来像重复记录了两遍。

**根因**
- `DebugLog` 同时把当前会话写入内存 buffer 和同一份 `debug_log.txt`。
- 查看页再把 `readPersistedLog()` 与 `getCurrentSessionLog()` 直接拼接，天然会把当前会话内容重复展示。

**解决方式**
- 启动时把上一轮 `debug_log.txt` 轮转为 `debug_log_previous.txt`，当前会话重新从空 buffer + 新文件开始。
- 查看页按“历史日志（上次运行） / 当前会话日志”分段读取不同来源，而不是继续拼接同一份数据。

**后续规则**
- 只要日志系统同时存在“历史持久化”和“当前内存态”，查看页就必须先定义边界，不能靠字符串拼接碰运气。

### 18. 聊天长会话发送抖动的第一嫌疑通常是整表刷新，不是单一滚动 bug
**现象**
- 聊天页里已有大量文字/图片时，发送新消息会出现整页闪动或像重新加载一遍的抖动感。

**根因**
- `MessageAdapter.submitList()` 使用 `items.clear() + addAll() + notifyDataSetChanged()`，会让长列表在状态变化时整表重绑。
- pending/confirmed 状态切换与自动滚底逻辑叠加后，抖动体感会进一步放大。

**解决方式**
- 为聊天消息补稳定 item id，并改成 `DiffUtil` 差量刷新。
- 自动滚底只在“用户接近底部 + 尾部新增/尾项确认完成”时触发，避免状态变化就抢焦点。

**后续规则**
- RecyclerView 一旦进入长会话/长列表场景，默认先排查是否存在整表 `notifyDataSetChanged()`；未排除前不要先把锅甩给滚动细节。

### 20. 媒体/文件下载接口发生异常时，不能继续沿用原始图片 Content-Type 回写 `ApiResponse`
**现象**
- 服务端文件下载链路在请求图片（如 `image/jpeg`）时，一旦进入异常分支，会抛出：
  `HttpMessageNotWritableException: No converter for [class com.flashnote.common.response.ApiResponse] with preset Content-Type 'image/jpeg'`。

**根因**
- `FileController.download()` 正常分支返回的是 `ResponseEntity<Resource>`，并会把响应头设置为具体媒体类型。
- 但当下载过程抛出 `BusinessException` 等异常时，请求会进入 `GlobalExceptionHandler`。
- 旧实现直接返回裸 `ApiResponse`，Spring 仍沿用原响应上下文中的 `image/jpeg`，导致它尝试把 `ApiResponse` 按 JPEG 写出并失败。

**解决方式**
- 保持文件下载成功分支继续返回 `ResponseEntity<Resource>`。
- 将 `GlobalExceptionHandler` 的异常响应统一改为 `ResponseEntity<ApiResponse<Void>>`，并显式设置 `Content-Type: application/json`，确保媒体请求异常时切回 JSON 错误响应。
- 已补 `GlobalExceptionHandlerTest`，验证业务异常和通用异常都会强制返回 JSON。

**后续规则**
- 二进制/媒体接口和 JSON 接口必须严格分流：成功返回流，异常返回明确的 JSON；不要依赖 Spring 在异常时自动纠正之前的媒体类型。
- 只要 controller 正常分支会手动设置 `image/*`、`video/*`、`application/octet-stream` 等内容类型，就必须检查对应异常处理是否也会错误继承该类型。

### 21. 媒体流下载中的 `ClientAbortException / connection reset` 优先按客户端中断处理，不要直接记成服务器内部错误
**现象**
- Android 与服务端处于稳定局域网环境时，服务端仍会偶发记录：
  `AsyncRequestNotUsableException: ServletOutputStream failed to write: java.io.IOException: 连接被对方重设`
- 堆栈落在 `ResourceHttpMessageConverter` / `FileController.download()` 写响应体阶段，但旧实现会被 `GlobalExceptionHandler.handleException(Exception)` 记成“服务器内部错误”。

**根因**
- 文件/图片下载成功链路本质是服务端持续向客户端写二进制流。
- Android 端的 Glide / ExoPlayer / 预览页在页面切换、关闭预览、列表重绑或生命周期结束时，可能主动取消请求或释放连接。
- 对这种“响应写出期间客户端提前断开”的情况，Tomcat/Spring 会抛 `ClientAbortException` / `AsyncRequestNotUsableException` / broken pipe / connection reset。
- 这类异常多数不是服务端业务 bug，而是客户端中断被错误归类成 500 噪音日志。

**解决方式**
- 后端 `GlobalExceptionHandler` 增加 `AsyncRequestNotUsableException` 专门处理，并在兜底异常里识别 `ClientAbortException` / `broken pipe` / `connection reset`，统一降级为 `warn`，返回 `204 No Content`。
- Android 聊天页关闭了额外的 `preloadRecentMedia()` 远端预加载，减少列表刷新时的重复媒体请求与生命周期取消噪音。
- 已补 `GlobalExceptionHandlerTest` 回归测试，验证 client-abort 分支不再走内部错误路径。

**后续规则**
- 文件/媒体流写出阶段看到 `ClientAbortException`、`AsyncRequestNotUsableException`、`Broken pipe`、`connection reset` 时，先判断是否为客户端主动中断，不要第一时间按 500/server bug 处理。
- Android 端对远端媒体的“列表预加载 + 预览页加载 + 播放器加载”要谨慎叠加；若无明确收益，优先减少额外预取请求，避免制造服务端断流噪音。

### 22. Spring Boot + Lombok 项目若主代码能编译但启动时报 `Unresolved compilation problems`，优先检查 Maven 注解处理链是否同时覆盖 compile 与 testCompile
**现象**
- 服务端启动时在 Bean 创建阶段报：
  `java.lang.Error: Unresolved compilation problems`
- 堆栈落在业务服务（如 `FlashNoteServiceImpl`）里，对实体的 `getId()/setId()`、`FlashNote::getUserId`、`Message::getContent` 等方法引用全部提示不存在。
- 同时 `mvn test` 的 `testCompile` 也可能出现大量实体 getter/setter “找不到符号” 错误。

**根因**
- 源码中的实体类依赖 Lombok `@Getter/@Setter` 生成访问器；若 Maven 编译器没有稳定执行 Lombok annotation processor，就会生成只有空构造器的 class。
- 主编译阶段和测试编译阶段都可能受影响；即使某次 `compile` 因缓存看似成功，`testCompile` 仍可能暴露出 Lombok 没有真正生效。
- 运行时一旦 Spring 加载到这类不完整 class，就会在 Bean 初始化阶段直接炸成 `Unresolved compilation problems`，看起来像“源码逻辑错了”，实际是编译产物坏了。

**解决方式**
- 在 `thunder-note-server/pom.xml` 的 `maven-compiler-plugin` 中显式配置：
  - `annotationProcessorPaths` 指向 Lombok
  - `testAnnotationProcessorPaths` 同样指向 Lombok
  - 统一声明 `lombok.version`
- 修复后必须做两层验证：
  1. `mvn clean compile`
  2. `mvn test`
- 若怀疑编译产物仍异常，可用 `javap -classpath target/classes <Entity>` 检查 getter/setter 是否真的生成。

**后续规则**
- 遇到 “源码里明明有 `@Getter/@Setter`，运行时或 testCompile 却说方法不存在” 的情况，先查 annotation processor，不要先怀疑业务代码。
- Maven + Lombok 项目中，不要只保证主编译链能跑通；测试编译链也必须显式覆盖 Lombok 处理器。
- 任何涉及“切环境 / 切站点 / 切租户”的改动，都要先回答本地事实源是否也一起切换；只换请求地址通常是不够的。

### 20. 后端定向 auth 测试失败时，先区分是否被既有 testCompile 基线阻断
**现象**
- 本次新增手势锁密文备份接口后，尝试运行定向 auth 测试时，Maven 先在 testCompile 阶段报多个旧测试仍引用不存在的 `com.flashnote.message.entity` 包，导致测试没能真正执行到 auth 用例。

**根因**
- 这是当前后端测试基线的既有编译问题，不是本次手势接口主代码引入的新错误。

**解决方式**
- 先用 `mvn clean compile` 验证主代码可编译，再结合 LSP diagnostics 与受影响测试文件做本次改动验证。
- 将 testCompile 基线问题单独记录，不与当前功能实现回归混淆。

**后续规则**
- 后续若跑后端定向测试却先死在 testCompile，先判断是不是测试基线问题；不要在未区分前就宣称“本次功能测试失败”。

### 21. Android 登录页如果直接消费旧的 `loginResponse`，切站或返回登录页时会出现“假登录”跳转
**现象**
- 用户退出登录后切换到另一个站点，甚至该站点不可达时，登录页仍可能先跳进主壳，随后才出现网络错误。

**根因**
- `LoginFragment` 观察的是 Activity 级 `AuthViewModel.loginResponse`。
- 如果回到登录页时没有显式重置旧登录态，新的 Fragment 会立刻收到上一次成功登录留下的 `loginResponse`，从而直接调用 `openMainShell()`。

**解决方式**
- 登录页进入时先 `resetLoginState()` 清掉旧 `authState / loginResponse / currentUser / errorMessage`。
- 成功消费本次真实登录响应后立刻 `consumeLoginResponse()`，避免返回登录页时再次被旧值击中。

**后续规则**
- 任何跨页面共享的登录结果 `LiveData` 都要明确“消费后清空”策略，尤其是登录页这种会频繁重建的入口页面。

### 22. 会话级依赖如果在登录前就按 `userId=-1` 初始化，首次登录后列表可能直到重启才显示数据
**现象**
- 第一次登录成功后，同步已经拉到了数据，但闪记列表页不显示；杀死 APP 重开后才出现。

**根因**
- `FlashNoteApp.initializeDependencies()` 旧实现会在应用启动时就创建依赖当前用户的 session-scoped repository。
- 这类仓储在构造阶段就会基于 `TokenManager.getUserId()` 绑定本地数据源；如果登录前提前创建，首次登录后 UI 仍可能继续观察旧的数据源。
- 更严重时，如果仓储实现对“未登录”直接抛异常，问题会从“首登列表不显示”升级为“首装冷启动直接闪退”（见 11.1）。

**解决方式**
- 登录/注册成功并持久化身份信息后，立即重建会话级依赖，再进入主壳。
- 更稳妥的基线是：这类 session-scoped 仓储默认延迟到用户态建立后再初始化，而不是先按匿名态创建再依赖后续补救。

**后续规则**
- 任何依赖“当前用户身份”的本地仓储/观察器，都不能默认跨登录生命周期复用；首次登录成功后要么重建依赖，要么延迟到用户态建立后再初始化。

### 23. 冷启动手势解锁页如果复用“返回到上页”语义，成功后可能出现错误回退甚至闪退
**现象**
- 设置完手势锁后，冷启动通过手势解锁进入应用时，成功后可能不是进入主壳，而是走错误的返回路径，严重时表现为闪退或退到后台。

**根因**
- 冷启动场景下，手势解锁页不是普通的“覆盖在已有主壳之上”的页面，而是登录后进入主内容前的门禁页。
- 如果成功后仍沿用“`popBackStack()` / `moveTaskToBack()`”这类普通返回语义，就会把冷启动门禁和普通前台复验混在一起。

**解决方式**
- 区分两种解锁来源：冷启动解锁成功后显式进入 `MainShell`；前台超时复验成功后才回退到原页面。

**后续规则**
- 同一个解锁页如果要复用于冷启动和前台复验，必须显式区分来源，并给出不同的成功后导航语义，不能把两种场景共用同一条“返回”逻辑。

### 24. Android 手势锁不能把系统选图返回误判成前台超时复验
**现象**
- 设置完手势锁后，从 App 内拉起系统图片选择器、文件选择器、相机或头像裁剪器，再返回当前页面时会直接进入手势解锁页，导致当前流程被打断。

**根因**
- `MainActivity.onStop()` 会统一记录一次“进入后台”的时间戳，`onResume()` 再统一调用 `maybeRequireGestureUnlockOnResume()`。
- 聊天页、卡片编辑器、闪记列表、资料编辑和头像裁剪等链路，都会通过系统 `ACTION_GET_CONTENT` / `ACTION_IMAGE_CAPTURE` / `UCrop` 拉起外部 Activity；这些流程返回时同样会触发 `onStop() -> onResume()`。
- 旧实现只对部分聊天图片选择入口做了一次性豁免，既没有覆盖相机/文件/裁剪，也没有覆盖其他模块。
- 旧的 `GestureUnlockResumeTracker` 只有单个布尔值，无法正确表达“连续两次受控外部返回”（例如选图后继续裁剪）这类链路。

**解决方式**
- 在 `ShellNavigator` / `MainActivity` 暴露统一的 `registerExternalFlowForGestureUnlockSkip()`，由宿主层集中登记“当前要进入一个可返回的外部流程”。
- 将 `GestureUnlockResumeTracker` 从单个布尔豁免升级为可计数消费：每次发起受控外部流程先登记一次，返回时只消费一次，这样 `选图 -> 裁剪` 这类两跳链路也不会漏。
- 当前已统一覆盖 `ChatFragment`、`CardEditorFragment`、`FlashNoteTabFragment`、`EditProfileFragment`、`ProfileTabFragment/ProfileAvatarHelper` 的图片、文件、相机与裁剪入口。

**后续规则**
- 任何会拉起系统 picker / 裁剪器 / 相机等外部 Activity，但语义上仍属于“当前任务继续完成”的流程，都必须通过宿主层统一登记一次外部流程豁免；不要再在单个页面里临时打补丁。
- 只跳过与本次外部返回对应的一次复验；冷启动手势门禁和真正离开 App 超时后的复验逻辑不能被这类豁免替代。

### 25. Android pending 队列如果把“失败后立即再派发”当成默认恢复机制，离线时会形成高速重发风暴
**现象**
- 离线情况下发送聊天消息，待同步列表里会出现同一条消息每秒被重发很多次；恢复网络后虽然消息最终可能发送成功，但过程里会产生明显的重试风暴。

**根因**
- `PendingMessageDispatcher.fail(...)` 旧实现会在把消息标记为 `FAILED` 后，立刻再次调用 `dispatchAllPendingNow()`。
- 同时 `dispatchAllPendingNow()` 会继续扫描 `STATUS_FAILED`，于是形成“失败 → 立刻重试 → 再失败 → 再立刻重试”的自旋。
- 当前链路没有退避/backoff，也没有在这个入口上做 attempt gate，所以离线时会被放大成高频请求风暴。

**解决方式**
- 将失败分支改为：只更新 `FAILED + errorMessage + attemptCount`，然后释放 `dispatchInProgress`，不再在同一次失败回调中立即扫全队列。
- 后续重试统一交由显式入口触发，例如用户点击重试、重新进入聊天会话、或恢复链路主动拉起，而不是在失败回调里自旋。

**后续规则**
- pending/outbox 的失败处理默认应是“记录失败并等待下一次恢复触发”，不要把“失败即刻再试”当成可靠性方案。
- 如果后续要做自动重试，必须显式设计退避、上限和触发边界，不能仅靠递归/链式派发。

### 26. Android pending 列表与 dispatcher 可派发状态不一致时，重启后会出现永久脏数据
**现象**
- APP 退出后再次进入，待同步列表仍保留旧条目；进入聊天窗口后消息可能会重发成功，但待同步列表对应条目不消失，手动同步也无效。

**根因**
- `PendingMessageRepositoryImpl` 会把 `PROCESSING / UPLOADING / UPLOADED / SENDING / FAILED / QUEUED` 都视为“待同步列表”数据源。
- 但 `PendingMessageDispatcher.canDispatch(...)` 只允许 `QUEUED / FAILED` 进入派发。
- 因此 APP 被杀时遗留的中间态（例如 `UPLOADING`、`SENDING`）会永久显示在待同步列表里，却又不会被重新派发或清理，造成列表状态与真实发送状态漂移。

**解决方式（已废弃，勿再采用）**
- 曾尝试在 `FlashNoteApp.initializeDependencies()` 后补一轮本地恢复：将上一轮中断留下的 `PROCESSING / UPLOADING / UPLOADED / SENDING` 统一重置为 `QUEUED`。
- 该方案会把 pending 恢复逻辑塞进冷启动/登录后的依赖重建路径，已验证会引入启动或登录回归，因此当前版本已回退，不再作为现行方案。

**当前方案**
- 目前以聊天页/统一 pending 派发链作为唯一消息重发入口，不在冷启动阶段自动恢复中间态。
- 待同步列表刷新通过 `PendingSyncAdapter` 深拷贝提交项 + 把 `payloadJson` 纳入 `DiffUtil` 内容比较收口，避免原地改状态导致 UI 无刷新。

**后续规则**
- 任何出现在“待同步列表”的状态，都必须同时回答两个问题：它是否还能被重新派发？何时会被清理？
- 如果某个状态只适合作为进程内瞬时态，就不要在重启后继续原样保留；必须在启动恢复阶段把它收口成稳定可处理状态。

### 25. Sync 按钮如果在主线程构建 Room 查询参数，会直接被 Room 拦截崩溃
**现象**
- 个人页点击“同步”按钮后立即闪退，日志报 `IllegalStateException: Cannot access database on the main thread`，堆栈落在 `MessageLocalDao_Impl.getLatestCreatedAt()`。

**根因**
- `ProfileActionHelper.triggerSync()` 直接从 UI 点击链路调用 `SyncRepositoryImpl.syncAll()`。
- 旧实现中 `SyncRepositoryImpl.pull()` 在发起网络请求前同步执行 `buildPullRequest()`，而 `buildPullRequest()` 会直接调用 `messageLocalDao.getLatestCreatedAt()` 读取 Room 数据库。
- 这段读取发生在主线程，命中 Room 的主线程保护并直接崩溃。

**解决方式**
- 将 `SyncRepositoryImpl.pull()` 中的 `buildPullRequest()` 与 `pushLocalState()` 中的本地 payload 构建统一搬到 `syncExecutor` 后台线程，再由后台线程发起 Retrofit `enqueue`。

**后续规则**
- 任何由 UI 点击直接触发的 repository/sync 动作，只要内部需要读取 Room 构造请求参数或 payload，都必须先切到后台线程；不能因为最终网络调用是异步的，就把前置 DAO 查询留在主线程。

### 27. 手动同步与聊天页不能保留两套消息发送链，否则会出现“聊天能发、同步报错”的双轨行为
**现象**
- 离线消息在进入聊天页后可以正常重发成功；但点击“我的-同步”按钮时，会出现 SQL 唯一冲突、后续消息不同步，甚至卡片消息退化成“未知卡片内容”。

**根因**
- 聊天页进入时走的是 `MessageRepository.retryAllPendingMessages()` / `PendingMessageDispatcher` 这条真实消息发送链。
- 手动同步旧实现则在 `SyncRepositoryImpl.syncAll()` 里额外构造 `payload.messages` 走 `/sync/push`，等于为消息保留了第二套同步方式。
- 两套路径并存后，消息确认、本地去重、卡片 payload 回写都可能出现时序分叉，最终表现为“聊天正常、同步异常”。

**解决方式**
- 手动同步当前先调用 `messageRepository.retryAllPendingMessages()`，统一复用聊天页同一条 pending 发送链。
- `SyncRepositoryImpl.buildLocalStatePayload()` 当前不再向 `payload.messages` 填充 pending 消息，彻底去掉第二套消息同步方式。

**后续规则**
- Android 侧消息发送/重发只能保留一个事实入口：`PendingMessageDispatcher`。
- sync 按钮可以继续负责拉取/刷新其他业务数据，但不能再自建另一套消息 push 协议来代替聊天发送链。

### 28. sync pull 如果只识别 `payload` 不识别 `payloadJson`，卡片消息会退化成“未知卡片内容”
**现象**
- 点击同步后，聊天里的卡片消息标题/摘要丢失，最终只显示“未知卡片内容”。

**根因**
- `SyncRepositoryImpl.toMessageLocalEntity()` 旧实现只处理 pull 响应里的 `payload` 字段，没有兼容 `payloadJson` 字符串字段。
- 一旦 sync pull 返回的是 `payloadJson`，本地 `messages_local.payload_json` 会为空，聊天渲染层就拿不到 `CardPayload`。

**解决方式**
- 当前实现同时兼容 `payload` 和 `payloadJson`：前者序列化后落库，后者直接作为 JSON 字符串写入 `payload_json`。

**后续规则**
- Android 对 Map 形态的 sync 响应做落库时，必须显式兼容对象字段与 JSON 字符串字段两种返回形态，尤其是卡片/复合消息这类 payload 驱动渲染的数据。

### 17. 语音消息时长必须沿 pending → server → local 全链路透传
**现象**
- 在线/离线发送语音后，当次显示正常；但重新进入页面、重启 APP，甚至重装后重新拉历史消息时，语音时长会丢成 `0s`。

**根因**
- `PendingMessageDispatcher.sendPendingMessage()` 发送语音消息时漏掉了 `message.setMediaDuration(...)`，导致服务端持久化的语音消息天然缺失时长。
- `MessageRepositoryImpl.persistRemoteMessages(...)` 在第一页全量回写本地时，只保留了旧的 `createdAt`，没有在远端时长缺失时回填本地已有的非零 `mediaDuration`。

**解决方式**
- 在 pending 发送到服务端前显式透传 `mediaDuration`。
- 在远端消息覆盖本地 `messages_local` 时，如果服务端返回的 `mediaDuration` 为空或非正值，则按 `clientRequestId` / `messageId` 回填本地已有的非零时长。

**后续规则**
- 媒体类消息（尤其语音/视频）新增字段时，必须按“pending 模型 → 出站 Message DTO → 服务端落库 → Room entity → UI 渲染”五段链路逐段核对，不能只看当次页面显示正确。

### 18. Android 代码治理红线必须显式写进文档，不能只靠口头提醒
**现象**
- Android Java 主链在阶段性重构后，容易再次回到“空 catch / `printStackTrace()` / 活跃页面硬编码文案 / Fragment 异步回调未判活 / 敏感日志裸输出”的旧习惯；如果不把规则落成文档，新会话很容易重复踩回去。

**根因**
- 这类问题横跨 UI、repository、工具类与日志链路，单靠某次代码修复无法长期约束。
- 过去整改重点放在“把这一次修好”，但没有把规则沉淀成后续可直接引用的 Android 侧红线。

**解决方式**
- 在 Android R2 收尾阶段把以下规则明确沉淀为可复用红线：
  - 禁止新增空 catch；
  - 禁止新增 `printStackTrace()` 作为正式错误处理；
  - 禁止新增用户可见硬编码文案到活跃页面布局；
  - Fragment 异步回调必须先过“已脱附 / state saved”检查；
  - 涉及 token / 用户敏感信息的日志默认脱敏或关闭。

**后续规则**
- 后续 Android 会话若涉及 UI、repository、日志、鉴权、Fragment 生命周期，默认先对照这五条红线自检；违反任一条都不应直接提交为完成态。
- 做资源治理时，优先从高频页面和高频提示文案开始，不要求一次性清空所有历史硬编码，但不能继续往活跃路径里新增新的硬编码。

### 16. Android 不能把业务成功码写死为 200
**现象**
- 闪记聊天里多选合并消息时，前端 Toast 提示“合并消息失败，Success”，但重新进入闪记后又能看到卡片消息已经成功生成。

**根因**
- 后端统一响应 `ApiResponse` 的成功码是 `0`，不是 HTTP 风格的 `200`。
- Android `MessageRepositoryImpl.mergeMessages()` / `mergeContactMessages()` 直接判断 `response.body().getCode() == 200`，导致 HTTP 成功 + 业务成功仍被误判为失败。

**解决方式**
- Android 统一改为使用 `response.body().isSuccess()` 判断业务成功，避免局部把成功码写死成 `200`。

**后续规则**
- Android 新接或改造接口时，优先复用统一 `ApiResponse.isSuccess()`，不要在 repository 中硬编码业务成功码。

### 17. 多附件临时文件名不能只精确到秒
**现象**
- 闪记卡片编辑器一次选择多张图片时，预览里可能出现多张相同图片；有时上传后卡片内容为空或只剩最后一张。

**根因**
- Android `CardEditorFragment.copyUriToTempFile()` 用 `yyyyMMdd_HHmmss` 生成缓存文件名；同一秒内处理多张附件时，多个 URI 会写到同一路径，后写入的文件覆盖先写入的文件，导致预览与上传都指向同一份临时文件。

**解决方式**
- 临时文件名改为“毫秒时间戳 + UUID”，确保每个附件都落到独立缓存文件。
- 保存按钮在附件复制处理中禁用，避免用户在后台复制未完成时提前提交。

**后续规则**
- Android 任何“多选文件/图片后转临时文件”的场景，都不能使用只精确到秒的文件名；至少补毫秒或随机后缀，并明确区分“处理中”和“可提交”状态。

### 18. Android 视频 remux 不能丢掉旋转元数据
**现象**
- 闪记卡片上传视频后，播放时画面方向发生旋转，和原始拍摄方向不一致。

**根因**
- `VideoCompressor` 使用 `MediaExtractor + MediaMuxer` 重新封装视频时，只复制了音视频轨道样本，没有把原文件的容器级旋转元数据传给新的 mp4。

**解决方式**
- 在 remux 前通过 `MediaMetadataRetriever` 读取 `METADATA_KEY_VIDEO_ROTATION`，并在 `MediaMuxer.start()` 前调用 `setOrientationHint()` 写回输出文件。

**后续规则**
- 后续 Android 任何“转码 / remux / 容器重写”视频的场景，都必须检查旋转信息、时长、音轨是否被保留，不能默认认为“复制轨道样本”就等于保留了所有展示信息。

### 19. Markdown 输入如果直接 `setText`，展示端一定会漏渲染
**现象**
- 通过富文本框输入的 Markdown 笔记，在聊天和卡片详情里会把 `#`、`-`、`**` 等语法符号原样显示出来。

**根因**
- Android 之前把文本消息、卡片文本项、`.md` 文件预览都按普通字符串 `setText(...)` 处理，没有引入 Markdown 渲染层。

**解决方式**
- 引入 `Markwon`，统一封装 `MarkdownRenderer`，给聊天文本消息、卡片详情文本项和 `.md` 文件预览复用同一套 Markdown 渲染逻辑。

**后续规则**
- 只要输入链路产出的是 Markdown 文本，展示端就必须显式走 Markdown 渲染；不能因为“底层还是字符串”就直接 `setText(...)`。

### 16. 后端 `mvn test` 失败时先区分是否为既有测试基线问题
**现象**
- 本次实现复合卡片消息第二步后，后端 `mvn clean compile` 通过，但 `mvn test` 在 `FlashNoteServiceImplTest` 编译阶段报 `NoSuchFileException: target/classes/com/flashnote/flashnote/dto/MatchedMessageInfo.class`。

**根因**
- 这是当前测试基线/构建产物层面的既有问题，不是本次 `message` 模块改动直接引入的业务编译错误。

**解决方式**
- 先用 `mvn clean compile` 验证主代码可编译，再单独记录 `mvn test` 的失败点，避免误判为当前功能实现回归。

**后续规则**
- 后续若再跑后端测试，看到 `MatchedMessageInfo.class` 丢失这类错误，先按“既有测试基线问题”处理，再决定是否单独修测试工程。

### 17. PostgreSQL `jsonb` 字段不能直接依赖默认 JacksonTypeHandler 写入
**现象**
- 复合卡片消息通过 `/api/messages/merge` 或普通发送接口落库时，报 `column "payload" is of type jsonb but expression is of type character varying`。

**根因**
- `Message.payload` 虽然声明了 `JacksonTypeHandler`，但 PostgreSQL `jsonb` 在写入时仍需要按 `Types.OTHER` 绑定；默认写法会把参数当成普通字符串传入数据库。

**解决方式**
- 为 `CardPayload` 单独实现 `jsonb` TypeHandler，在 `setNonNullParameter` 中按 `Types.OTHER` 写入 JSON 串，并在 `Message.payload` 上显式使用该处理器。

**后续规则**
- 后续若新增 PostgreSQL `jsonb` 字段，不要默认复用普通字符串处理逻辑；优先补专用 TypeHandler 并验证真实插入链路。

**后续规则**
- 后续遇到难以定位的异常时，优先查看调试日志面板获取完整堆栈。

### 12. 后端返回类型变更导致 Android JSON 解析失败
**现象**
- 上传文件时 Android 报 `java.lang.IllegalStateException: Expected a string but was BEGIN_OBJECT at line 1 column 39 path $.data`

**根因**
- 后端 `FileController.upload()` 返回类型从 `ApiResponse<String>` 改为 `ApiResponse<FileUploadResult>`（包含 objectName 和 originalFilename），但 Android `FileService.java` 仍声明为 `Call<ApiResponse<String>>`。Gson 尝试将 JSON 对象解析为字符串时抛出异常。

**解决方式**
- 创建 Android 端 `FileUploadResult` 模型类，更新 `FileService` 和 `FileRepositoryImpl` 的返回类型，从返回对象中提取 `objectName`。

**后续规则**
- 后端接口返回类型变更时，必须同步检查并更新 Android Retrofit 接口声明。
- 特别注意 `ApiResponse<T>` 的泛型参数 T 必须与后端实际返回的 JSON 结构匹配。

### 13. 删除闪记需级联删除关联消息
**现象**
- 删除闪记后，孤立消息仍留在数据库中。

**根因**
- `FlashNoteServiceImpl.deleteNote()` 只做了闪记的软删除（`setDeleted(true)`），未处理关联的消息记录。

**解决方式**
- 在 `deleteNote()` 中软删除闪记后，追加 `messageMapper.delete(where flashNoteId = noteId)` 硬删除关联消息。

**后续规则**

### 14. Android Enter 键行为与 IME 配置冲突
**现象**
- EditText 配置了 `inputType="textCapSentences|textMultiLine"` 和 `imeOptions="flagNoEnterAction"`，但按 Enter 仍发送消息而非换行。

**根因**
- `ChatFragment.setupMessageInput()` 中注册了 `OnEditorActionListener`，其中 `KEYCODE_ENTER` 分支拦截了所有 Enter 按键事件并调用 `sendMessage()`，覆盖了 XML 中的多行配置。

**解决方式**
- 移除 `KEYCODE_ENTER` 处理块，仅保留 `IME_ACTION_SEND` / `IME_ACTION_DONE` 的处理。Enter 键默认行为（换行）由系统和 XML 配置自动处理。

**后续规则**
- 多行输入的 EditText 不应在 EditorActionListener 中拦截 `KEYCODE_ENTER`。

### 14. 媒体消息发送后出现两条重复
**现象**
- 发送图片/视频/文件/语音后，聊天列表中同一条消息出现两次。退出 APP 重新登录后恢复为一条。

**根因**
- `ChatFragment` 在发送媒体消息时先调用 `addLocalMessage()` 添加一个乐观预览（id 为 null），然后 `sendMessage()` 在服务器返回成功后又把服务端返回的消息追加到列表中。本地临时消息从未被移除。

**解决方式**
- 在 `MessageRepositoryImpl.sendMessage()` 的 `onResponse` 成功回调中，先 `updated.remove(message)` 移除乐观预览消息（按对象引用匹配），再 `updated.add(apiResponse.getData())` 添加服务端返回的完整消息。

**后续规则**
- 任何使用"先乐观添加、后真实替换"模式的场景，都必须确保真实返回时移除旧条目，不能只追加。

### 15. 媒体消息转发只发送文字占位符
**现象**
- 长按图片/视频/语音/文件消息进行转发时，目标闪记中只收到 `[图片]`、`[视频]` 等文字，没有实际媒体。

**根因**
- `showForwardDialog()` 调用 `sendTextToFlashNote()` 只传递了 `message.getContent()`，完全忽略了 `mediaType`、`mediaUrl`、`fileName` 等媒体字段。

**解决方式**
- 在转发逻辑中判断 `message.getMediaType()` 是否存在。若为媒体消息，构造新的 `Message` 对象并复制所有媒体字段，通过 `sendMessageToFlashNote()` 发送完整消息。

**后续规则**
- 任何涉及消息复制/转发/引用的逻辑，都必须检查并保留完整的媒体字段，不能只取 content 文本。

### 16. RecyclerView 按钮太小导致点击无响应
**现象**
- 合集页面中，除第一个以外的合集编辑/删除按钮点击无响应。

**根因**
- `item_collection.xml` 中编辑/删除按钮只有 20dp x 20dp，加上 2dp padding，实际可触摸面积极小。在部分设备上触摸区域被父布局或相邻子视图拦截。

**解决方式**

**后续规则**
- RecyclerView item 内的可操作元素（按钮、图标）最小可触摸面积应为 48dp x 48dp（Material Design 规范）。

### 17. 根视图 setOnLongClickListener 拦截所有子控件点击
**现象**
- 聊天页所有按钮（媒体容器、语音播放、文件点击等）点击无响应。

**根因**
- `MessageAdapter.bind()` 中对 `binding.getRoot()` 设置了 `setOnLongClickListener`，Android 会隐式将该视图标记为 `clickable=true` 和 `longClickable=true`，导致根布局拦截所有子控件的触摸事件。

**解决方式**
- 将长按监听从根视图移到具体的消息气泡容器（`bubbleCard` 和 `rightContainer`），避免根布局拦截子控件点击。

**后续规则**
- 在 RecyclerView item 中设置长按监听时，不应挂在最外层根视图上，而应挂在具体的内容容器上。

### 18. postDelayed 100ms 但 recordingSeconds++ 计时导致 10 秒显示 1:40
**现象**
- 录音计时器 10 秒就显示一分钟以上。

**根因**
- 录音 Runnable 以 100ms 间隔运行，但每次回调都执行 `recordingSeconds++`，导致 100ms 被当成 1 秒累计，10 真实秒 = 100 次回调 = recordingSeconds=100。

**解决方式**
- 拆分为两个独立 Runnable：计时 Runnable 每 1000ms 递增秒数并更新文本，振幅 Runnable 每 100ms 更新波形。两者在停止录音时同时移除回调。

**后续规则**
- 当一个定时任务需要不同频率的子任务（如 UI 更新 vs 动画更新）时，必须拆分为独立 Runnable，不能混用同一间隔。

### 20. pending 重试入口若仍按“Text”命名，会和实际媒体重试能力产生契约漂移
**现象**
- P1-5 失败恢复链路补齐后，聊天页失败消息（包括图片/文件/语音/视频）都已经可以通过同一个重试入口重新入队并继续走 dispatcher，但代码里如果仍保留 `retryPendingText(...)` / `retryAllPendingText()` 这类命名，后续维护很容易误以为重试只支持文本。

**根因**
- `MessageAdapter` 的失败重试图标是按“mine + pending failed”统一开放的，`PendingMessageDispatcher` 也已经按 mediaType 处理文本与媒体状态机；真正的限制条件是 `status == FAILED`，不是 `mediaType == TEXT`。
- 如果接口名继续写成 Text，会出现“行为是通用 pending，契约却像文本专属”的语义漂移。

**解决方式**
- 将 Android 侧重试接口统一更名为通用 pending 语义：`retryPendingMessage(localId)`、`retryAllPendingMessages()`。
- 删除重试入口里无副作用的死调用，避免测试和代码一起围绕无意义查询建立错误契约。

**后续规则**
- 只要 pending/outbox 主链已经覆盖多种 mediaType，重试/恢复接口命名就必须使用通用语义，避免把“状态驱动能力”误写成“文本专属能力”。
- 对于 Room / dispatcher 这类状态机链路，测试应优先断言“同一条 pending 被复用并继续推进”，不要把内部读取/更新次数写死成脆弱实现细节。

### 21. P1-6 风控开关不要一刀切到所有消息类型，最小回退范围应只覆盖文本 pending 主链
**现象**
- 进入 P1-6 后需要满足“保留 Feature Flag 或最小开关位，便于快速回退到 P0 路径”。如果直接给整个消息发送系统做总开关，容易把已经稳定落到 `PendingMessage + Dispatcher` 的图片/文件/语音/视频链路一起切回旧页面内存路径，反而扩大回退风险。

**根因**
- 当前代码里，文本发送入口和媒体发送入口已经不是同一条实现：
  - 文本仍可在 repository 层保留“旧直发”实现；
  - 媒体已经统一收口到 `enqueueMedia(...)`，并依赖 pending 状态机处理上传/压缩/失败恢复。
- 如果回退开关同时作用于媒体，就会违背 P1-6 本身的约束：“文本稳定前，不允许把媒体链路全部切到新实现”的反面也成立——不能为了文本回退把媒体整条主链重新打散。

**解决方式**
- 新增最小风控开关位，仅控制文本 pending 主链：`MessageFeatureFlags.ENABLE_TEXT_PENDING_PIPELINE`。
- `MessageRepositoryImpl.sendTextInternal(...)` 在开关关闭时回退到旧直发 `sendMessageInternal(...)`；媒体 `enqueueMedia(...)` 不受该开关影响，始终继续走 pending + dispatcher 主链。
- 用单测分别锁住三件事：文本关闭回退直发、文本开启继续 pending、媒体不受文本开关影响。

**后续规则**
- 需要“快速回退”时，优先做**最小影响面开关**，不要把不同成熟度的链路绑成一个总闸。
- 当系统同时存在“文本先稳定、媒体后收口”的分阶段策略时，开关设计必须和阶段边界一致，否则回退本身会制造新的跨链路回归。

### 22. Android 离线优先必须先建“本地真源 → 后台恢复 → 真机补证”三段式，不要跳步
**现象**
- 容易一上来先接 WorkManager、后台恢复或 sync 执行器，但此时页面仍主要吃网络回包 / 内存 `LiveData`，或者 confirmed 仍只存在 repository 内存里。
- 也容易在已有 `PendingRecoveryWorker` / `pullAndRefreshLocal()` 后，过早把“后台链已完成”当成“完整离线优先已完成”。

**根因**
- 如果 UI 还不以本地表为单一事实源，后台任务只是在旧架构外面再套一层触发器。
- 如果聊天 confirmed 不落本地表，pending/outbox 即使已经稳定，聊天页仍不是真正本地优先。
- 如果 Worker 只是发起异步动作就立刻 `Result.success()`，那它只代表“恢复已发起”，不代表“恢复已完成”。

**解决方式**
- 先建本地真源：列表 / confirmed / favorites 等页面优先改为“网络写本地，UI 观察本地”。
- 再建后台恢复：`PendingRecoveryWorker` 只做 repository 级动作，如 `retryAllPendingMessages()` + `pullAndRefreshLocal()`，不直接碰 UI。
- 最后做真机补证：跨重启、登录后恢复、冷启动恢复、失败后恢复网络等场景必须单独验证。

**后续规则**
- 做离线优先时，**先验证本地真源是否成立，再接后台执行器**；不要把 WorkManager 当成离线优先本身。
- confirmed 与 pending 必须拆职责：pending 继续做状态机，confirmed 落本地表，不要混成一个超级内存模型。
- Worker 必须等待关键恢复结果并在需要时返回 `Result.retry()`，不能把“发起恢复”误写成“恢复完成”。
- 本地表必须尽早补 `userId` 隔离；若仍用 `fallbackToDestructiveMigration()`，只能算过渡方案。

### 40. Android 当前应按“主链已接通，剩余问题在收口”来判断优先级
**现象**
- 后续会话若只凭旧印象，容易把 Android 继续误判成“collection / favorite / profile 还是壳层”，从而把任务重心放错。

**解决方式**
- 判断 Android 当前状态时，至少核对 repository、Room、本地表观察链、worker/sync 是否真实接通。
- 当前默认优先看 `docs/完整开发计划.md`：
  - `3.5.5 P2`（主链数据流）
  - `3.5.7`（代码治理）
  - `3.5.8`（剩余可执行 backlog）

**后续规则**
- 不再默认把 `collection / favorite / profile` 归类为壳层未接通；当前剩余问题重心在 sync、恢复链、生命周期边界、Profile 收口和验证补强。

### 41. Android 恢复链要同时区分“单测覆盖”和“每轮手工补证”
**现象**
- pending/outbox、后台恢复、登录后恢复、冷启动恢复等链路，即使已有 Room / Worker / repository 测试，也仍可能在真实设备路径上不稳定。

**解决方式**
- 代码/单测覆盖：payload 组装、本地状态机推进、FAILED-only 重试、worker 触发前置条件。
- 每轮手工补证：文本 pending、图片 pending、视频 processing、失败后恢复网络、登录后恢复、冷启动恢复。

**后续规则**
- 后续 Android 会话若修改 `PendingRecoveryWorker`、`SyncRepositoryImpl`、`MessageRepositoryImpl`、`ChatFragment` 中任一恢复链相关路径，默认补一轮“代码验证 + 手工补证”组合，不要只凭 build 通过判定完成。

**固定手工回归矩阵（直接执行）**
- 文本 pending：发送文本后立即退后台再回来，确认消息仍可见且状态继续推进。
- 图片 pending：发送图片后切 tab / 返回闪记列表再回来，确认不会残留假 `uploading` 占位。
- 视频 processing：发送视频后离开页面再回来，确认处理中的状态仍可见且最终能收口。
- 失败重试：断网发送任一消息后恢复网络，确认失败项可通过现有恢复链继续推进。
- 登录后恢复：存在 `QUEUED/FAILED` 项时重新登录，确认 `PendingRecoveryWorker` 会触发最小恢复链。
- 冷启动恢复：强杀应用后重新打开，确认最小恢复链会重新触发，且不会直接把页面状态误判为完成。

**验证分工**
- 自动化优先：payload 组装、worker 前置条件、FAILED-only 重试、repository 状态推进。
- 真机必做：跨重启、登录后恢复、离页后媒体处理、失败后恢复网络。

> 注：具体执行项统一以 `docs/完整开发计划.md` 的 `3.5.8 Android 剩余可执行 backlog` 为准；本经验库只保留判断规则，不再重复列 backlog。

### 20. CollectionAdapter 按钮 click 用 lambda 闭包捕获 bind 参数导致复用异常
**现象**
- 合集页只有第一个合集的编辑/删除按钮有效。

**根因**
- `bind()` 方法中用 lambda 捕获 `group` 参数设置 click listener，在 RecyclerView 复用 ViewHolder 时可能因闭包引用过期。

**解决方式**
- 将 click listener 移到 ViewHolder 构造函数中，使用 `getBindingAdapterPosition()` 实时取当前 position 对应的数据项，避免闭包捕获过期引用。

**后续规则**
- RecyclerView ViewHolder 的 click listener 应使用 `getBindingAdapterPosition()` 而非 bind 参数闭包，以确保复用场景下数据正确。

### 21. RecyclerView 滚动加载连环触发导致一次性加载全部消息
**现象**
- 聊天页进入后默认查到了所有消息，而非最近 20 条。

**根因**
- 滚动监听器条件 `findFirstVisibleItemPosition() == 0` 过于宽松，初始滚动到底部的动画过程中经过 position=0，连续触发多次 loadMore，直到全部消息加载完。

**解决方式**
- 滚动触发条件改为 `!recyclerView.canScrollVertically(-1)`（到顶才触发）。
- 增加 `isLoadingMore` 防抖标志，`isInitialScrollCompleted` 初始保护，`hasMoreMessages` 终止条件。
- 修正 `getHasMore()` 返回正确的 hasMore LiveData 而非错误返回 isLoading。

**后续规则**
- 分页加载的滚动监听需要完整的防抖机制：加载中锁、初始化保护、无更多数据终止。

### 22. Profile 页布局可点击不等于已接点击事件
**现象**
- 「我的」页所有入口（编辑简介、修改密码、设置、退出登录、调试工具、头像）点击均无响应。

**根因**
- `fragment_profile_tab.xml` 虽配置了 `clickable/focusable`，但 `ProfileTabFragment.onViewCreated()` 未绑定任何 `setOnClickListener`，导致 UI 有点击态但无业务处理。

**解决方式**
- 在 `ProfileTabFragment` 新增统一 `setupClickActions()`，绑定头像、菜单项到 `showAvatarPicker/showEditBioDialog/openChangePassword/openSettings/openDebug/logout`。

**后续规则**
- 新页面上线前必须做“布局可点击控件 ↔ Fragment 监听绑定”一一核对，避免只配 XML 不接逻辑。

### 23. BottomNavigationView 长按提示可用消费长按事件统一关闭
**现象**
- 底部导航长按会弹出提示文字，影响体验。

**根因**
- Material `BottomNavigationView` 默认对 item 长按展示 tooltip/label。

**解决方式**
- 在 `MainShellFragment` 中对每个菜单项执行两层处理：
  - `setTooltipText(null)` / `MenuItemCompat.setTooltipText(null)`
  - 对 itemView 设置 `setOnLongClickListener(v -> true)` 消费长按事件。

**后续规则**
- 需要完全禁用底部导航长按提示时，优先“清 tooltip + 消费长按”组合，不依赖单一 API。

### 24. Repository 错误 LiveData 不清空会在切 tab 时反复弹旧错误
**现象**
- 断网后出现 `Failed to connect ...`，网络恢复后切换底部 tab 仍重复弹旧错误。

**根因**
- Repository 的 `errorMessage` 是单例 LiveData，失败后写入错误但未清空；
- 页面重建或重新观察时，新 observer 会立即收到上次缓存错误并再次 Toast。

**解决方式**
- 为 `FlashNote/Collection/Favorite/Message` Repository 增加 `clearError()`；
- ViewModel 在 `refresh/bindFlashNote` 前清错；
- Fragment 在 Toast 后调用 `clearError()` 消费事件；
- 成功回调中同步 `clearError()`，确保恢复网络后不会保留脏错误。

**后续规则**
- 长生命周期单例仓库中的错误状态必须可消费/可清空，不能把错误当普通状态长期保留。

### 25. 媒体消息布局高度异步变化会导致首次进入未滚到底
**现象**
- 某闪记最新一条是图片/视频时，进入聊天页偶发停在半屏，需手动下滑到底。

**根因**
- `submitList` 后立即 `scrollToPosition(last)`，但图片/视频高度在 Glide 解码后才最终确定，初次滚动位置失准。

**解决方式**
- 新增 `scrollToBottomAfterLayout()`：立即滚一次 + 下一帧再滚一次；
- 若末条为 IMAGE/VIDEO，再延迟两次补偿滚动，确保媒体高度稳定后仍在底部。

**后续规则**
- 对高度异步变化列表（图片/视频）不要只滚一次；至少做“下一帧补偿滚动”。

### 26. 冷启动多图会出现“从无到有”卡顿，可通过预加载与缓存优化缓解
**现象**
- 会话含多图时，冷启动首次进入明显看到图片逐张加载；热返回同会话体验正常。

**根因**
- 首次进入时尚未建立内存缓存，且列表只在 bind 阶段被动加载。

**解决方式**
- `MessageAdapter` 增加 `preloadRecentMedia()`，对最近媒体消息做 Glide 预加载；
- 图片/视频加载链加 `thumbnail(0.25f)` + `dontAnimate()` 降低首屏突变；
- `RecyclerView` 设 `setItemAnimator(null)` 与较高 `setItemViewCacheSize` 减少重绘抖动。

**后续规则**
- 媒体会话首屏优化优先做“预加载 + 缩略图占位 + 降低列表动画开销”三件套。

### 27. 服务层新增依赖后，先补兼容构造器或同步改单测
**现象**
- 后端服务新增 `FileService` 依赖后，`mvn test` 在 testCompile 阶段直接失败，报 `MessageServiceImpl`、`FlashNoteServiceImpl` 构造器参数数量不匹配。

**根因**
- 现有单测大量直接 `new ServiceImpl(...)`，当构造器签名变化时，测试代码不会自动适配。

**解决方式**
- 在服务实现里保留向后兼容构造器（测试专用），并在新逻辑里对可选依赖做空值保护。
- 同时优先在主构造器保留真实依赖注入，避免运行时行为退化。

**后续规则**
- 每次改 service 构造器签名前，先全局检索测试实例化点；要么同批量改单测，要么提供兼容构造器，避免 CI/testCompile 阶段阻断。

### 28. Android `testDebugUnitTest` 与 `lint` 需先区分“既有失败”与“本次引入失败”
**现象**
- 本轮改动后执行 `./gradlew assembleDebug test lint`，`testDebugUnitTest` 因 `AuthRepositoryImplTest` 的 `Looper not mocked` 失败，`lint` 因 `VideoCompressor` 的 `WrongConstant` 失败。

**根因**
- 两处失败均来自仓库既有问题：
  - `AuthRepositoryImplTest` 在本地 JVM 单测中触发 Android Looper 依赖；
  - `VideoCompressor` 中 `MediaExtractor` flag 直接赋给 `MediaCodec.BufferInfo.flags`，属于历史 lint 问题。

**解决方式**
- 分开执行并记录验证结果：
  - `assembleDebug`（通过）用于确认本轮代码可编译打包；
  - `testDebugUnitTest`、`lint` 明确标注既有失败项和报告路径，避免误判为新回归。

**后续规则**
- Android 验证失败时，必须附失败来源和报告路径，并明确是否为新增回归；若是既有失败，后续单独建修复任务，不要在功能改动中静默吞掉。

### 29. MyBatis-Plus 默认策略下，`updateById` 对 null 字段可能不会落库
**现象**
- 删除合集后，后端逻辑已执行“把关联闪记 `tags` 置空”，但列表里仍显示已删除合集名，随后在客户端编辑该分组会提示“未找到合集记录”。

**根因**
- `flash_notes.tags` 在实体默认更新策略下，`updateById` 传入 null 时可能被忽略，导致“逻辑置空”未真正更新到数据库。

**解决方式**
- 在后端实体 `FlashNote.tags` 增加 `@TableField(updateStrategy = FieldStrategy.ALWAYS)`，确保 `tags=null` 能被正常写回；保留原有 `updateById` 路径，兼容现有单测期望。

**后续规则**
- 凡是业务语义包含“清空字段”的场景，必须显式确认该字段的更新策略支持 null 落库；否则会出现“看起来改了，实际没落库”的伪成功。

### 30. 外部分享应优先使用原始文件名，避免缓存文件名污染接收端
**现象**
- 聊天消息长按分享文件时，外部 App 常看到带对象名/时间戳的缓存文件名，难以识别文件真实含义。

**根因**
- 分享 URI 直接指向缓存文件（对象名或临时名），未在分享阶段映射到消息里的原始文件名。

**解决方式**
- 分享前按 `message.fileName` 在 `cache/share/` 生成同名副本，再通过 `FileProvider + ClipData + FLAG_GRANT_READ_URI_PERMISSION` 对外分享。

**后续规则**
- “上传文件名”和“分享展示名”是两个维度：上传链路可用内部名，但对外分享必须以用户可识别的原始文件名为准。

### 31. emoji 头像场景需要清理本地图片缓存优先级
**现象**
- 用户把头像从图片切换为 emoji 后，界面可能出现历史图片头像（尤其在聊天消息里）。

**根因**
- 聊天头像逻辑会在 emoji 分支下继续读取本地 `avatar.jpg` 作为回退，导致旧图覆盖新 emoji。

**解决方式**
- emoji 头像更新成功后，清理本地 `avatar.jpg`；并在聊天头像赋值逻辑中，emoji 分支显式清空 `localAvatarFile`，避免历史缓存抢占优先级。

**后续规则**
- 当头像支持“图片 URL + emoji”双形态时，必须明确缓存优先级：emoji 绝不能回退到历史图片缓存。

### 32. Android 单测失败项会随基线演进变化，验证时必须记录“本轮失败签名”
**现象**
- 本轮执行 `./gradlew testDebugUnitTest` 时，失败签名变为 `AuthRepositoryImplTest > register_failure_returnsError`（`RuntimeException`），不再是此前记录的 `Looper not mocked`。

**根因**
- Android 单测基线并不稳定，历史失败项可能在仓库演进后发生“失败位置迁移”或“失败类型替换”。

**解决方式**
- 本轮仍按“先确认可编译打包、再记录单测失败签名”的方式执行：
  - `assembleDebug` 通过；
  - `testDebugUnitTest` 失败签名已更新并记录到本条；
  - `lint` 仍命中既有 `VideoCompressor` 的 `WrongConstant` 问题。

**后续规则**
- 每次执行 Android 验证，都要落地记录“当前真实失败签名 + 报告路径”，不要沿用旧条目的失败描述。

### 34. 上传完成回调必须绑定原始目标会话，不能临时读取当前聊天
**现象**
- 媒体上传完成后，如果用户已切到别的聊天页，图片/视频/文件/语音消息可能发到当前打开的新聊天，而不是发起上传时的原聊天。

**根因**
- 聊天上传链路历史上在回调完成时读取 `ChatViewModel` 当前的 `flashNoteId/peerUserId`，而这些值可能已经被后打开的聊天页覆盖。

**解决方式**
- 在发起上传时就捕获原始 `flashNoteId/peerUserId`，并把它们带到上传完成回调中。
- `ChatFragment` 新增统一 helper，将图片/视频/文件/语音上传完成后的发送动作显式路由到原始目标会话。
- `ChatViewModel.sendMedia(...)` 也改为优先使用 `Message` 自带的 `flashNoteId/receiverId`，避免再依赖可变的当前会话状态。

**后续规则**
- 任何“异步完成后再发送/保存/落库”的链路，都不能在回调里临时读取“当前页面/当前会话”状态；必须在操作开始时捕获原始目标并一路透传。
- 如果一个问题表现为“切页面后结果落到了别的对象/别的上下文”，先排查目标 ID 是否是在回调完成时动态读取的。

### 33. Spring Boot 重启时若 8080 被占用，需切换端口并记录实际联调地址
**现象**
- 本轮执行 `mvn spring-boot:run` 时，服务在 Flyway 完成后报 `java.net.BindException: 地址已在使用`，Tomcat 无法绑定 8080。

**后续规则**
- 本地重启服务端时，先确认端口占用；若端口冲突，优先切备用端口并同步给客户端联调配置，不要假定 `18081` 一定空闲。

### 34. 引入“收集箱虚拟闪记（ID=-1）”后，需要同步校正会话键避免冲突

### 40. 收集箱快速收集上传的状态回写不能绑在 FlashNoteTabFragment 生命周期上
**现象**
- 从闪记列表悬浮 `+` 选择图片/文件后，若立刻进入收集箱再退出，上传过程可能被页面切换打断观感：占位消息一直显示“上传中”旋转，但实际上传没有继续完成或失败状态也没有落回 UI。

**根因**
- `FlashNoteTabFragment.handleCaptureMedia()` 会先插入本地乐观占位消息（`uploading=true`），再异步调用 `fileRepository.upload(...)`。
- 旧逻辑在上传成功/失败回调最前面直接判断 `!isAdded() || getActivity() == null`，导致页面切走后即使网络回调回来，也会提前 `return`，业务状态没有回写。
- 结果是本地会话列表里的临时消息一直停留在 `uploading=true`，`MessageAdapter` 会持续显示旋转进度。

**解决方式**
- 将“业务状态回写”和“页面 UI 提示”拆开：
  - 上传成功后，无论 `FlashNoteTabFragment` 是否仍在前台，都先执行 `message.setUploading(false)`、回写远端 `mediaUrl` 并继续 `sendMessage(...)`；
  - 只有 Toast、按钮动画、列表刷新这类 UI 反馈才放在 `runIfUiAlive(...)` 内按页面存活状态执行。
- 为 `MessageRepository` 增加 `removeLocalMessage(...)`，当上传失败或发送失败时主动删除本地假占位，避免留下持续旋转的假消息。

**后续规则**
- 任何“先插本地乐观占位、再异步上传/发送”的链路，都不能把业务状态收口绑在 `Fragment/Activity` 是否仍然存活上。
- 生命周期判断只能保护 Toast、动画、滚动、导航等 UI 副作用，不能阻断 `uploading/failed/sent` 这类真实状态回写。
- 若异步链路失败后本地临时项已无恢复价值，必须显式清理；否则就必须显式写入失败状态，不能留在“永远进行中”。

### 43. Android 文件下载不能在 Retrofit 主线程回调里直接读网络流，缓存命中也不能只看“非 0 字节”
**现象**
- Android 上传文件后立即打开，APP 仍会退出；下次重新进入 APP 再打开同一文件时，调试日志显示先命中本地缓存，再出现 `PDF preview failed`。
- 调试日志捕获到两段关键证据：
  - `Open cached file: ... size=6296 ... ext=pdf`
  - `android.os.NetworkOnMainThreadException`，堆栈指向 `FileRepositoryImpl$2.onResponse(FileRepositoryImpl.java:92)`。

**根因**
- `FileRepositoryImpl.download()` 虽然使用了 Retrofit `enqueue()`，但真正的 `body.byteStream().read(...)` 仍写在 `onResponse()` 回调里；当前 Android 端 `ApiClient` 未自定义 Retrofit callback executor，回调会回到主线程，因此网络流读取实际发生在 UI 线程并触发 `NetworkOnMainThreadException`。
- 下载被中断或异常响应落盘后，`MessageAdapter.openFileMessage()` 仍只按 `cacheFile.exists() && cacheFile.length() > 0` 判断缓存可用，导致 6296 字节这类残缺 PDF 也会被当成有效缓存再次打开。
- `FilePreviewActivity.showPdfPreview()` 的 `PdfRenderer` 只是最终暴露问题的位置，不是这轮问题的原始根因；它报 `Unable to load the document!` 是因为前面已经拿到了坏缓存文件。

**解决方式**
- 将 `FileRepositoryImpl.download()` 中的 `InputStream.read()` + 文件写入完整搬到后台线程执行，只保留成功/失败结果通过主线程回调通知 UI。
- 保留“临时文件下载完成后再 rename 成正式缓存”的原子替换策略，避免下载中途留下半成品覆盖正式文件。
- 对 PDF 缓存增加最小有效性校验：不能再只看“文件存在且大于 0”；命中异常缓存时先删除，再重新下载。
- 下载完成后在成功回调前补一次最小合法性兜底，避免把错误响应体或截断文件直接落成正式缓存。

**后续规则**
- Android 上使用 Retrofit `enqueue()` 不等于“回调里的代码天然在后台线程”；凡是 `onResponse()` 中涉及 `InputStream.read()`、大文件写盘、解压、转码等重活，必须显式放到后台线程。
- 文件缓存命中规则不能只看“存在 + 非 0 字节”；对 PDF、媒体、压缩包这类结构化文件，至少要做轻量合法性校验后再复用。
- 当日志同时出现“损坏缓存预览失败”和“下载时主线程网络异常”时，优先把两者串成同一条链路排查，不要误把 `PdfRenderer` 当成唯一根因。
  - 上传与发送继续在回调中后台完成。
- 同时保留失败时的状态收口逻辑：如果用户仍留在当前页，则恢复按钮状态并展示错误提示。

**后续规则**
- 对“收集/上传/发送”类重操作，默认优先做成异步派发，不要强迫用户停留在编辑页等待完成。

  - `chatViewModel.removeLocalMessage(message)`；
  - 页面仍存活时再 toast 提示失败。
- 将多处直接 `requireActivity().runOnUiThread(...)` 的发送链路 UI 收尾改为统一 `runIfUiAlive(...)`，只在页面仍有效时滚动到底部或提示。

### 46. Android 顶部 Header 区域高度与标题居中的正确实现方式
**现象**
- 闪记列表页、联系人列表页、合集页、收藏页四个 Tab 的顶部灰色区域高度不一致，标题文字水平位置也不统一。

**根因**
- 早期实现混用了 `FrameLayout` 和 `LinearLayout`，且对居中效果的实现方式理解有误：
  - `LinearLayout + layout_weight=1 + gravity=center` 只能实现"剩余空间居中"，不是屏幕绝对居中；
  - `FrameLayout + wrap_content` 的 `layout_gravity="center"` 受多子视图高度差异影响，导致标题视觉重心偏移。

**解决方式**
- 统一使用 `FrameLayout` 作为 Header 容器，固定高度 `48dp`；
- 标题使用 `layout_gravity="center"` 实现屏幕绝对居中（不受右侧按钮影响）；
- 右侧按钮使用 `layout_gravity="center_vertical|end"` 靠右且垂直居中；
- 各页面结构统一为：`FrameLayout(48dp) → View(0.5dp divider) → Content`。

**后续规则**
- Android 顶部导航区域设计时，若需"标题绝对居中 + 右侧按钮靠右"，必须用 `FrameLayout + 固定高度 + layout_gravity` 组合，不依赖 `LinearLayout weight` 的剩余空间居中。

### 49. 后端排障时应优先看统一 API 请求/响应日志，先关闭 MyBatis SQL stdout 降噪
**现象**
- 联调排查时间字段、请求体污染或接口返回异常时，仅依赖 MyBatis stdout SQL 容易把中间 SQL 参数误读成最终接口入参或最终数据库状态。

- MyBatis `StdOutImpl` 打印的是某次 mapper 执行时的 SQL 与绑定参数，不等于最终 API 请求体、最终返回体或最终持久化结果。
- 后端此前只有全局异常日志，缺少统一的接口级请求/响应事实链路。

**解决方式**
- 后端统一新增 controller 级 API 请求/响应日志，固定打印：接口名、请求参数、响应参数。
- 对 `MultipartFile`、`HttpServletRequest/Response`、`BindingResult` 等特殊对象做过滤或摘要化，避免日志失控。
- 在排障阶段先关闭 MyBatis `StdOutImpl`，避免 SQL stdout 淹没接口级日志。

**后续规则**
- 以后优先根据“接口名 + 请求参数 + 响应参数”判断问题属于请求构造、业务逻辑还是响应回写，不要先拿 SQL stdout 当最终事实。
- 只有在需要继续下钻 mapper/实体问题时，再按需打开 SQL 级日志；默认不要长期依赖 MyBatis stdout 作为主排障视角。

### 50. Android 去掉 `allowMainThreadQueries()` 后，Retrofit 主线程回调里的 Room 收口也必须一起迁走
**现象**
- P1-1 文本待发送链路把 pending 查询切到 Room `LiveData`、并移除 `allowMainThreadQueries()` 后，发送文本一度出现“点击发送立即闪退”。

**根因**
- 文本入队、单条重试等入口已切到后台线程，但 `PendingMessageDispatcher` 里 `messageService.send(...).enqueue(...)` 的 `onResponse/onFailure` 仍运行在主线程。
- 回调里继续直接执行 `findByLocalId/update/delete` 等 Room 操作，导致在移除 `allowMainThreadQueries()` 后命中 Room 主线程访问限制。
- 同时，repository 里的 `LiveData + HashMap` 合并状态若与后台 DAO 回调混用，也会放大线程边界风险。

**解决方式**
- 保持 DAO 读写继续留在 dispatcher 自己的单线程 executor；不要在 Retrofit 主线程回调里直接碰 Room。
- `listener.onPendingUpdated(...)` 改为统一切回主线程执行，只让 repository 的内存态 / `LiveData` 合并逻辑在主线程更新。

**后续规则**
- 以后凡是把 Room 从主线程迁走，必须同时检查 Retrofit/异步回调是否仍在主线程里执行 DAO 收口，不能只改“入口插入”而漏掉“成功/失败回调”。
- Android 仓库里如果一层负责 DAO 读写，另一层负责 `LiveData` / 内存缓存更新，就要明确线程边界：DAO 后台执行，UI/仓储状态主线程执行。

### 51. 聊天合并列表如果先按消息来源排序，会直接破坏严格时间顺序
**现象**
- P1-1 文本待发送链路接通后，聊天页出现“发送更晚的消息排在发送更早的消息前面”的现象。

**根因**
- `MessageRepositoryImpl` 的合并比较器曾先按 `remote/pending` 来源分桶，再按 `createdAt` 排序。
- 一旦两条消息来源不同，即使时间先后明确，也会先被来源优先级打乱，无法保证严格按时间排序。

**解决方式**
- 合并比较器改为先按 `createdAt` 排序，再在时间相同的情况下用来源和稳定 tie-breaker 兜底。
- 保留 pending/confirmed 合并展示，但不要让“来源”压过“时间”。

**后续规则**
- 聊天消息只要对外承诺“按时间展示”，比较器第一排序键就必须是时间；来源、状态、临时 ID 只能做 tie-breaker。
- 后续如果继续做 pending/confirmed 去重或替换，不要再把 source bucket 放到时间前面，否则排序问题会反复出现。

### 52. 聊天分页切页键必须和最终展示排序键一致，不能后端按 id 分页、前端按时间展示
**现象**
- 聊天页即使把合并比较器改成 `createdAt` 优先，历史消息里仍会出现“晚发消息排在早发消息前面”的问题。

**根因**
- 后端消息列表接口曾按 `id DESC` 切页，再在页内 reverse 成升序；Android 最终展示则按 `createdAt` 做时间排序。
- 一旦分页切片依据和最终展示依据不一致，跨页边界就可能把时间更晚的消息切进“更早历史页”里，客户端即使再次 sort 也只能重排已拿到的集合，修不了切错页的问题。

**解决方式**
- 后端消息列表接口统一改为按 `createdAt DESC, id DESC` 切页，再 reverse 成升序页返回。
- 客户端与服务端统一按“时间优先、id 兜底”理解消息顺序，避免一端按 id、一端按时间造成页边界错位。

**后续规则**
- 以后只要列表支持分页，服务端切页排序键必须和客户端最终展示排序键一致；否则跨页错序问题无法靠客户端二次排序根治。
- `id` 只能作为同时间戳下的稳定次排序键，不能替代 `createdAt` 成为聊天消息的主排序语义。

### 53. 文件下载接口若返回 `InputStreamResource`，统一 API 响应日志会提前消费流
**现象**
- Android 重新安装后，聊天图片、头像等认证媒体资源请求已到达后端，`/api/files/download` 日志显示先返回 `200 OK`，随后同一请求链路又抛出 `InputStream has already been read`，客户端图片持续空白。

**根因**
- 后端 `FileController.download()` 直接返回 `ResponseEntity<InputStreamResource>`。
- 新增的 `ApiLoggingAspect` 会对 controller 返回值执行 `objectMapper.writeValueAsString(response)` 记录响应日志。
- Jackson 序列化 `InputStreamResource` 时会触发 `getInputStream()`，提前消费 MinIO 返回的单次流；随后 Spring 再写 HTTP 响应时二次读取同一流，触发 `IllegalStateException`。

**解决方式**
- `ApiLoggingAspect` 对 `ResponseEntity<Resource>` 做特殊分支，流式响应只记录状态码与 header 摘要，不再尝试 JSON 序列化 body。
- `FileController.download()` 改为先读取 MinIO 流到 `byte[]`，再以 `ByteArrayResource` 返回，并补齐 `contentLength`、按文件名推断 `Content-Type`、`Content-Disposition:inline`。

**后续规则**
- 以后凡是 controller 返回 `Resource/InputStream` 一类流式响应，统一日志层都不能再序列化 body；只能记录元信息。
- 文件下载接口若要兼容 Glide / 浏览器内联展示，优先返回可重复读取的资源包装，并补正确的 MIME type 与 `inline` disposition。

### 54. 服务端修复下载流后，Android Glide 仍可能命中旧的错误磁盘缓存
**现象**
- 服务端文件下载接口修复后，请求已稳定返回 `200 OK`，但 Android 新安装版本里聊天图片、头像、联系人头像等仍会显示空白；服务端日志能看到 `GET /api/files/download` 命中。

**根因**
- 服务端故障期间，Glide 曾把同一 URL 的 500 错误响应体写入磁盘缓存。
- 服务端修复后，Android 继续优先读取这些旧缓存条目，而不是重新拉取真实图片字节，导致“服务端正常、客户端仍空白”的假象。

**解决方式**
- Android 保留正常图片缓存策略，不对头像/媒体长期关闭缓存。
- 在 `FlashNoteApp` 增加一次性的 Glide 磁盘缓存清理逻辑：通过本地 `cache_clear_version` 版本号控制，仅在包含本次修复的新版本首次启动时后台清理一次脏缓存。

**后续规则**
- 当服务端曾向同一媒体 URL 返回错误体时，客户端修复后要优先排查 Glide / 图片库是否仍在命中旧的错误缓存，而不是继续怀疑鉴权链路。
- 对“由服务端错误响应污染的媒体缓存”这类问题，优先使用“一次性升级清缓存”策略，不要长期关闭缓存以规避历史脏数据。

### 55. pending 与 confirmed 合并展示若不按 `serverMessageId` 去重，成功回写瞬间会出现逻辑双条
**现象**
- P1 文本待发送链路接通后，聊天列表虽然已经能同时显示本地 pending 和远端 confirmed，但某些消息发送成功的瞬间会短暂出现两条内容相同的逻辑消息：一条是本地 pending 投影，一条是服务端正式消息。

**根因**
- `MessageRepositoryImpl` 已经有 `mergedConversations = remote confirmed + pending cache` 的雏形，但旧实现只是简单把 pending UI 消息追加到 merged 列表中，再按时间排序。
- 当 dispatcher 成功回调把服务端正式消息写入 remote 列表，而对应 pending 行尚未删除或 merged 层没有识别映射关系时，同一条逻辑消息会同时存在于 remote 和 pending 两个数据源中。

**解决方式**
- 在 merged helper 里先建立 remote 消息 ID 集合，再遍历 pending：
  - 若 `pending.serverMessageId` 已命中 remote 正式消息，则跳过该 pending 的 UI 投影；
  - 其余 pending 再转成 `Message` 进入 merged 列表。
- 保留 `localSortTimestamp` 作为 pending / confirmed 的统一排序投影，确保成功替换前后消息位置稳定。

**后续规则**
- 以后只要聊天列表采用“remote + pending”双源合并，就必须显式定义去重键；最小可用键优先选 `serverMessageId`，后续再补 `clientRequestId` 级别的更强映射。
- 去重逻辑必须放在 repository 的 merged 层，不能指望 Adapter 或页面层靠 `notifyDataSetChanged()` 运气消重。

**补充说明（2026-03-25）**
- 之后已补完整契约：服务端 `messages` 表新增 `client_request_id`，并在 `send/list` 的正式消息模型中回传 `clientRequestId`；Android merged layer 现已优先按 `clientRequestId` 做一对一映射去重。
- 当前保守文本指纹规则降级为兼容兜底，只在旧数据或缺少 `clientRequestId` 的场景下参与去重，避免把更激进的内容相似度规则误用到媒体或系统消息上。

**后续规则补充**
- 只要要实现稳定的 pending/confirmed 合并替换，不能只靠 Android 本地猜测；必须把 `clientRequestId` 这样的稳定请求键从客户端发送链路贯穿到服务端落库与查询回包。
- `serverMessageId` 适合处理“pending 已被服务端确认”的显式映射，`clientRequestId` 才是避免成功回写瞬间双条的主键；文本指纹只应作为兼容兜底，不应长期充当主去重策略。

### 56. 媒体预加载必须跳过本地临时路径，不能把未上传文件当成远端资源 URL
**现象**
- 聊天页会对最近图片/视频做 Glide 预加载；如果列表里混有本地临时媒体消息，预加载阶段可能把 `/data/...`、`file://...` 这类本地路径错误送进远端 URL 解析，造成无意义的加载失败和噪音。

**根因**
- `MessageAdapter.preloadRecentMedia(...)` 过去只根据 `isUploading()` 跳过“上传中”消息，但对已经不处于 uploading、却仍可能持有本地临时路径的消息没有额外保护。
- 在 P1/P1.4 过渡阶段，媒体消息链路仍有“本地文件路径先挂到 `mediaUrl`，上传成功后再替换成远端 objectName”的旧路径，因此仅靠 `isUploading()` 还不够安全。

**解决方式**
- 在 adapter 里增加本地路径判断：若 `mediaUrl/thumbnailUrl` 以 `file://` 或绝对路径 `/` 开头，则跳过 Glide 远端预加载与图片/视频缩略图加载。

**后续规则**
- 只要媒体消息仍处于“本地路径 → 远端 URL”迁移态，Adapter 侧就必须把“本地路径是否可直接展示”作为显式判断条件，不能默认所有 `mediaUrl` 都能走 `MediaUrlResolver.resolve()`。
- 真正的长期解法仍是 P1-4：把 `localFilePath` 与 `remoteUrl` 的职责完全分离，不再复用同一个字段混装本地/远端语义。

### 57. 最小 outbox 执行器不要只支持单条 dispatch，聊天页重进和调试页手动同步都要能补触发
**现象**
- 文本 pending 主链接通后，如果执行器只暴露 `dispatch(localId)`，那么只有“新建 pending 当下”或“用户点击失败重试”这两类场景能推进。
- 一旦用户切出聊天页再回来，或者希望在调试页手动触发恢复，`QUEUED/FAILED` 项会继续停在本地，不会被重新扫描推进。

**根因**
- 旧版 `PendingMessageDispatcher` 虽然已经是单线程 executor，但能力仍停留在“单条 localId 推进”，没有“按会话扫描推进”或“全局扫描推进”入口。
- 这样执行器仍然隐式依赖当前页面的即时发送动作，达不到 P1-3 对最小 outbox 的要求。

**解决方式**
- 保留现有 `PendingMessageDispatcher`，不要再新建第二套执行器；直接在其上补：
  - `dispatchConversation(...)`：扫描当前会话下的 `QUEUED/FAILED` 项；
  - `dispatchAllPending()`：扫描全局 `QUEUED/FAILED` 项。
- `MessageRepositoryImpl.bindFlashNote/bindContact` 在聊天页重进时自动补触发当前会话扫描。
- 调试页同步成功回调里补一次 `retryAllPendingText()`，作为手动恢复入口。

**后续规则**
- 只要系统里已经有“pending store + dispatcher”，就必须提供**批量补触发入口**，不能只留下 `dispatch(localId)` 这种一次性入口。
- 最小 outbox 的目标不是“发送时能跑一次”，而是“离开页面、回来、手动同步后仍能继续推进”；否则它仍然只是半个页面内临时队列。

> 注：离线优先、本地真源、后台恢复、批量补触发与真机补证的当前执行入口，统一以 `docs/完整开发计划.md` 的 `3.5.8 Android 剩余可执行 backlog` 为准。

### 58. 媒体 pending 主链不能继续放在 ChatFragment 里串 upload→send，必须先 enqueue 再交给 dispatcher
**现象**
- 图片/文件发送若继续沿用旧的 `ChatFragment` 页面内存链路（`addLocalMessage -> fileRepository.upload -> sendMessage -> removeLocalMessage`），一旦用户切页、重建 Fragment 或上传中断，媒体状态就只存在于当前页面对象里，无法恢复。

**根因**
- 旧版媒体入口直接在页面层创建 `Message` 占位对象，并把本地文件路径塞进 `mediaUrl`，随后立即在 Fragment 内串上传与发送。
- 这会让媒体 pending 生命周期隐式依赖页面实例，和 P1/P1-3 已经建立的 `PendingMessage + Dispatcher` 主链割裂。

**解决方式**
- 对 `IMAGE / FILE` 第一阶段先做最小收口：
  - `PendingMessage` 持久化 `localFilePath / remoteUrl / fileName / fileSize`；
  - `MessageRepository.enqueueMedia(...)` 只负责写 pending 行并触发 dispatcher；
  - `PendingMessageDispatcher` 接入 `FileRepository`，执行 `QUEUED -> UPLOADING -> UPLOADED -> SENDING -> SENT / FAILED`；

### 59. Android repository 新增跨仓能力时，优先走构造注入，不要直接依赖 `FlashNoteApp` 单例
**现象**
- 本次为“收集箱清空消息”给 `FlashNoteRepositoryImpl` 接 `MessageRepository` 后，`FlashNoteRepositoryImplTest` 既有 9 条单测全部在构造阶段 `NullPointerException`。

**根因**
- 直接在 repository 构造函数里调用 `FlashNoteApp.getInstance().getMessageRepository()`，把原本可直接 new / mock 的仓储变成了对 Application 单例的硬依赖；Robolectric 单测没有走真实 App 装配链，因此立即 NPE。

**解决方式**
- 改为构造注入 `MessageRepository`，并保留原三参构造兼容既有测试。
- 生产环境在 `FlashNoteApp.initializeDependencies()` 中显式传入 `messageRepository`；测试继续使用原三参构造。

**后续规则**
- Android repository / use-case 层新增跨仓能力时，优先用构造注入，不要直接从 `FlashNoteApp` 或其他全局单例取依赖。

### 60. Android 改动验证必须一路跑到资源、Java、D8、单测四个关口
**现象**
- 本次聊天多选面板新增“删除”按钮后，第一次 `assembleDebug` 先因不存在的 `@color/logo_primary` 失败；修完资源后继续下探，又暴露出 D8 / 单测阶段的真实问题。

**根因**
- Android 构建是分阶段暴露问题：资源链接、Java 编译、D8/dex、单元测试分别是不同关口。前一层错误修完后，后一层问题才会显露。

**解决方式**
- 先把资源引用修成现有色值（如 `@color/primary`），再继续完整跑 `./gradlew assembleDebug` 与 `./gradlew test`，直到 D8 和单测也通过。

**后续规则**
- Android 功能改动完成后，至少执行 `./gradlew assembleDebug` + `./gradlew test`；不能因为“资源修好了”或“Java 编译过了”就提前宣布完成。

### 61. 本地缩略图占位不要只考虑远端 URL，离线视频首帧也必须立即渲染
**现象**
- 离线发送视频时，pending 里其实已经生成了本地首帧缩略图文件，但聊天列表仍然显示空白占位，看不到视频首帧。

**根因**
- `showVideoMessage()` 之前只在 preview 不是本地路径时才走 Glide 渲染，等于把本地缩略图路径直接跳过了；结果是“生成了缩略图，但 UI 不展示”。

**解决方式**
- 视频消息预览统一走 `resolveMediaModel(preview)`，允许 Glide 直接加载本地文件路径。
- 这样离线 enqueue 后，视频消息会立即显示本地首帧；待网络恢复上传成功后，再平滑切到远端 `thumbnailUrl`。

**后续规则**
- 任何“先本地占位、后远端回写”的媒体链路，都必须同时验证：本地文件路径能否直接被 UI 预览层消费，不能只验证上传后的远端 URL。

### 62. 缩略图质量不要压得过狠，首轮可先调到 240px / JPEG 82 再观察体积
**现象**
- 200px + JPEG 70 在聊天图片/视频缩略图上会明显发糊，尤其是文字截图和边缘细节较多的内容。

**根因**
- 当前场景不是极限带宽优化，聊天列表更需要“清晰可辨”而不是极端压缩；70 质量对这类缩略图偏激进。

**解决方式**
- 将 `ThumbnailUtils` 调整为 `240px / JPEG 82`，在体积与清晰度之间取更平衡的折中。

**后续规则**
- 聊天缩略图优先保证“文字可读、主体可辨”；若用户主诉发糊，先调质量和边长，再考虑更复杂的编码策略。

### 63. 网络恢复后的 pending 恢复发送要串行推进，否则完成时序竞争会打乱离线原始顺序
**现象**
- 大量消息离线发送后，网络一恢复，消息会并发上传/发送，最终聊天列表里的顺序和用户离线发送时的顺序明显不一致。

**根因**
- 恢复逻辑原本会一次 dispatch 多条 `QUEUED/FAILED` 消息，谁先上传完成、谁先拿到服务端回包，谁就先落 confirmed，本质上是“完成时序”覆盖了“入队时序”。

**解决方式**
- `PendingMessageDispatcher` 增加串行门闩：同一时刻只推进一条 pending，成功或失败后再递进触发下一条。
- confirmed 回写本地时继续保留 pending 的离线入队时间投影，减少本地刷新时的排序漂移。

**后续规则**
- 只要用户对“发送顺序”有稳定预期，恢复链路就应优先保证串行语义；除非明确允许乱序，否则不要为了吞吐量默认并发恢复。

### 64. 聊天页自动滚动必须尊重用户手动滚动意图，pending 高频更新时不要反复强拉到底部
**现象**
- 离线连续发送很多消息时，聊天列表会因为 pending 状态频繁变化不断触发自动滚动；用户一旦尝试手动上滑，页面会立刻被拉回原位置，出现“滑不动/抖动”的体感。

**根因**
- `ChatFragment` 的消息 observer 之前只要列表更新就会调用 `scrollToBottomAfterLayout()`；再叠加 enqueue 成功回调的主动滚底，pending 高频更新时就形成连续抢焦点。

**解决方式**
- 引入 `autoScrollEnabled + isNearBottom()` 保护：只有当用户当前就在底部附近时，消息更新才自动跟随到底部。
- 用户手动上滑后关闭自动跟随；等用户自己回到底部，才重新恢复自动滚动。
- 进一步收紧触发条件：只有**尾部新增消息**或**尾部那条消息从 uploading 变成发送成功**时，才允许自动滚动；单纯 `QUEUED/UPLOADING/SENDING/FAILED` 状态抖动不应触发滚底。

**后续规则**
- 任何聊天/时间线页面的自动滚动，都应先判断“用户是否仍在底部附近”；不要把“有新内容”直接等同于“必须立刻滚到底部”。
- 对 pending/outbox 场景，要额外区分“消息内容新增”与“同一条消息状态变化”，前者才可能需要跟随，后者默认不应打断用户手势。

### 65. 闪记列表页悬浮 `+` 入口不能单独维护“本地假消息 + 直传直发”分支，必须复用聊天页 pending/outbox 主链
**现象**
- 闪记列表页悬浮 `+` 的“消息 / 图片 / 文件 / 卡片”如果走了独立发送逻辑，就会出现和聊天窗不一致的行为：离线直接报网络失败、收集箱没有本地占位、没有统一重试。

**根因**
- `FlashNoteTabFragment` 之前的图片/文件/相机入口绕开了 `MessageRepository.enqueueMedia(...)`，自己维护了一套 `addLocalMessage -> upload -> sendMessage` 的直发链；这条链天然没有 pending/outbox 语义。
- 快速文字/卡片入口虽然能走发送链，但收集箱列表本身没有本地 `latestMessage` 预览更新，所以离线时看起来像“没占位”。

**解决方式**
- 媒体入口统一改成 `messageRepository.enqueueMedia(COLLECTION_BOX_NOTE_ID, ...)`。
- 快速文字与卡片保存成功后，通过 `fragmentResult` 把 `inbox_preview` 回传给 `FlashNoteTabFragment`。
- `FlashNoteRepositoryImpl` 提供 `updateInboxPreviewLocally(...)`，直接更新本地 `flash_notes_local.latest_message`，让收集箱条目在离线时也能立刻显示占位摘要。

**后续规则**
- 同一个“发送到收集箱/会话”的能力，只允许有一条主发送链；列表页入口、聊天页入口、快捷编辑器入口都必须复用同一个 pending/outbox 语义，不能再各写一套本地占位和网络发送逻辑。
  - `ChatFragment` 的图片/文件/拍照入口只负责采集文件并 enqueue，不再自己维护 pending 生命周期。

**后续规则**
- 只要媒体消息要支持切页恢复或失败重试，就必须先落 `PendingMessage`，再交给 dispatcher 推进；页面层不能再直接串完整生命周期。
- 第一阶段可以先只切 `IMAGE / FILE`，把 `VOICE / VIDEO` 留到后续单独收口；不要把压缩、上传、发送三层状态一次性混进同一个大改里。

### 59. 只改 Room 实体不升级数据库版本，会在进入聊天页首次访问 pending 表时直接闪退
**现象**
- P1-4 第一阶段给 `PendingMessage` 增加 `fileName / fileSize` 等持久字段后，已安装旧版本 App 的设备进入聊天页会立刻闪退。

**根因**
- `FlashNoteDatabase` 仍然保持 `version = 1`，但 `PendingMessage` 实体字段已经变化。
- 聊天页进入时会读取 `pending_messages` 表；Room 在首次访问该表时发现实体 schema 与本地数据库 schema 不一致，直接抛异常。

**解决方式**
- 将 `FlashNoteDatabase` 版本提升到 `2`，让现有 `fallbackToDestructiveMigration()` 生效，旧 schema 自动重建为包含新列的表结构。

**后续规则**
- 只要 `@Entity` 持久字段发生变化，就必须同步评估并更新 Room database version；不能只改实体类后直接继续联调。
- 如果 pending/store 是聊天页启动就会访问的关键表，这类 schema 漏升级会直接表现为“进入页面即闪退”，优先检查数据库版本而不是先猜页面空指针。

### 60. VIDEO 不能直接复用 IMAGE/FILE 的 upload→send 两段链路，必须先抽出“压缩/预处理”阶段
**现象**
- 如果把 `VIDEO` 和 `IMAGE/FILE/VOICE` 一样直接丢进“先 upload、再 send”的链路，页面层就不得不继续在 `ChatFragment` 里自己处理压缩、临时文件替换和失败提示，视频主链仍然依赖页面实例，切页后无法保证状态恢复。

**根因**
- `VIDEO` 比图片/文件/语音多一个前置处理阶段：压缩（当前实现由 `VideoCompressor` 承担）。
- 旧版 `handleVideoPicked()` 把“本地占位 → 压缩 → 上传 → 发送”整条链路都写在 Fragment 里，导致：
  - 页面销毁后视频 pending 生命周期丢失；
  - 压缩失败只能在页面层 toast，无法沉淀到 pending 状态表；
  - 测试只能碰 UI 入口，无法稳定覆盖状态推进。

**解决方式**
- 引入 `VideoPreparationService` 作为可注入的压缩/预处理边界，dispatcher 不再直接依赖 `VideoCompressor` 静态调用。
- `PendingMessageDispatcher` 新增 `STATUS_PROCESSING`，将视频主链扩展为：
  - `QUEUED -> PROCESSING -> UPLOADING -> UPLOADED -> SENDING -> SENT / FAILED`
- `ChatFragment.handleVideoPicked()` 改为和其他媒体入口一致，只负责采集文件并 `enqueueMedia("VIDEO", ...)`，由 dispatcher 接管后续处理。

**后续规则**
- 只要某类媒体在上传前还需要“压缩/转码/预处理”，就必须把这个阶段显式纳入 dispatcher 状态机，不能继续让 Fragment 自己串完整生命周期。
- 对带前置处理阶段的媒体链路，优先抽象出可注入 service（如 `VideoPreparationService`），否则很难写稳定单测，也容易把业务逻辑锁死在 UI 层。

### 61. 媒体 pending 成功回写正式消息时，必须把本地元信息补到 `serverMessage`，否则语音时长等展示会丢失
**现象**
- 离线发送语音后，pending 可以自动重发成功，但正式消息渲染出来的语音时长显示为 `0s`。

**根因**
- `PendingMessage` 中已经持久化了 `mediaDuration / fileName / fileSize / remoteUrl`，但 `MessageRepositoryImpl.onPendingUpdated()` 在拿到服务端正式消息时，只补了 `localSortTimestamp`，没有把这些本地元信息同步到 `serverMessage`。
- 服务端当前正式消息模型不一定回传完整媒体元信息，因此 merged 层若不主动补齐，UI 会拿到一个缺字段的正式消息对象。

**解决方式**
- 抽出 `applyPendingMetadataToServerMessage(...)`，在 pending 成功回写正式消息时，把 `mediaType / mediaUrl / mediaDuration / fileName / fileSize` 等字段从 pending 补到 `serverMessage`。

**后续规则**
- 只要服务端正式消息模型还不能保证完整回传所有媒体展示字段，pending→confirmed 替换时就必须做一次“本地元信息补齐”，否则重发成功后的 UI 很容易出现时长、文件名、大小丢失。

### 62. 失败态本地媒体不能继续沿用播放/打开行为，否则用户只会看到“地址无效”而不是明确失败提示
**现象**
- 离线发送视频失败后，聊天列表里依然能点视频卡片；点击后不会提示“发送失败”，而是进入播放器再看到“视频地址无效”。

**根因**
- 失败态 pending 的 `mediaUrl` 仍可能是本地临时路径；如果 adapter 继续沿用正常成功态的播放/打开逻辑，播放器收到的并不是有效远端地址，最终表现成“地址无效”的误导性报错。

**解决方式**
- `MessageAdapter` 对 `VIDEO / VOICE` 失败态且仍是本地路径的消息，不再继续绑定播放/打开行为，而是直接提示“发送失败，请重试”。

**后续规则**
- 媒体失败态的交互要优先反映“发送失败”这一事实，不能继续复用成功态的打开/播放逻辑；否则用户看到的是下游组件的地址错误，而不是上游发送失败的真实原因。

### 66. 文件下载成功后立刻打开闪退，优先检查“回调线程 + 外部打开异常兜底”
**现象**
- 聊天/收藏里上传文件后点击打开，客户端偶发闪退；服务端日志显示上传与下载请求都成功，`/api/files/download` 返回 200，`Content-Type` 与 `Content-Length` 正常。

**根因**
- `FileRepositoryImpl` 的 upload/download 回调此前未强制切回主线程；上层回调里包含 Toast、页面跳转与文件打开等 UI 操作，在线程不一致场景会触发运行时异常。
- 文件外部打开链路对 `FileProvider.getUriForFile(...)` / `startActivity(...)` 的异常兜底不足，路径、权限、可处理应用缺失等异常会直接中断流程。

**解决方式**
- 在 `FileRepositoryImpl` 内统一通过 `Handler(Looper.getMainLooper())` 分发成功/失败回调，保证上层 UI 操作主线程执行。
- 在 `MessageAdapter.openFileWithExternalApp()` 与 `FilePreviewActivity.openExternal()` 中补齐防御：
  - 打开前校验本地文件存在且可读；
  - 调用 `resolveActivity(...)` 预判是否有可处理应用；
  - 捕获 `ActivityNotFoundException`、`IllegalArgumentException`、`SecurityException` 并记录 `DebugLog`，降级为可见错误提示。

**后续规则**
- 只要 repository 回调会上抛到 UI 层（Toast/导航/启动 Activity），必须统一约束线程语义，避免“看似偶发”的跨线程闪退。
- 文件打开链路必须把“找不到应用”“URI/权限异常”“文件不可读”区分并兜底，优先保证“不闪退 + 可诊断”。

### 67. Android 共享错误 LiveData 如果在每个页面都直接 Toast，离线时一定会刷屏
**现象**
- 断网或弱网时，闪记、联系人、收藏、合集、资料页会频繁弹出 `Network error...`、`获取资料失败...`、`同步失败...` 一类提示；用户切换 tab 或重新进入页面时，这些提示会反复出现。
- 同时，删除消息、文件下载准备、卡片入队、资料保存、头像更新等成功/进度提示也会持续打断操作流，和页面本身已经可见的状态反馈重复。

**根因**
- 多个页面共用 repository / viewModel 的 `errorMessage` 通道，但各自 `observe(...)` 后直接 `Toast(error)`；页面初始化或切回页面时又会触发新的 refresh，于是离线错误在多个 tab 上被重复放大。
- 很多操作已经有列表状态、按钮 loading、上传占位、失败图标等可见反馈，但 UI 仍额外叠加“成功/准备中” Toast，造成重复提示。
- 部分 UI / helper 的 catch 或 onError 分支只做 Toast，没有统一落到 `DebugLog`，导致既吵又不利于排障。

**解决方式**
- 在 `DebugLog` 增加“疑似网络错误识别 + 重复 Toast 时间窗口节流”能力，作为 UI 层统一复用的最小治理能力。
- `FlashNoteTabFragment`、`ContactTabFragment`、`FavoriteTabFragment`、`CollectionTabFragment`、`ProfileTabFragment`、`EditProfileFragment` 等页面改为：
  - 网络/离线类错误优先 `DebugLog`，默认不再重复 Toast；
  - 非网络类错误才在必要时保留一次性提示。
- 删除或收敛以下成功/进度提示：
  - 消息删除成功 / 批量删除成功；
  - 文件“正在下载/正在准备分享”；
  - 卡片“已加入发送队列”；
  - 收集箱“已加入待发送”；
  - 资料保存成功 / 简介更新成功 / 同步完成 / 头像更新成功。
- 主入口如 `MainActivity`、`MainShellFragment` 的创建阶段异常先写 `DebugLog`，保证崩溃前至少有线索落盘。

**后续规则**
- 只要页面已有明确的可视状态反馈（按钮 loading、列表项 uploading/failed、局部 UI 变更），就不要再叠加同一语义的成功/进度 Toast。
- 共享错误通道不能在每个 tab 里简单地“observe 后直接 Toast”；至少要先区分网络类/业务类，再决定是否提示。
- 离线/网络类错误默认优先沉淀到调试日志，避免用户切页时被相同错误反复打断。
- 所有 catch / onError 分支都应优先补 `DebugLog`，Toast 只能是补充反馈，不能替代排障日志。

### 经验 68：MediaStore 保存文件到 Download/ThunderNote 的同名去重策略

**场景**
保存媒体文件到公共 `Download/ThunderNote` 目录时，用户可能多次保存同一文件，需要避免静默覆盖。

**问题**
- Android 10+ 使用 `MediaStore.Downloads` 插入文件，系统不会自动阻止同名文件（部分厂商 ROM 行为不一致）。
- Android 9- 直接写文件到 `Environment.getExternalStoragePublicDirectory(DIRECTORY_DOWNLOADS)/ThunderNote/`，同名则覆盖。

**解决方式**
- Android 10+：插入前先通过 `ContentResolver.query()` 查询 `MediaStore.Downloads`，匹配 `DISPLAY_NAME` + `RELATIVE_PATH = "Download/ThunderNote/"`，若已存在则尝试 `name(1).ext`、`name(2).ext`……最多到 999。
- Android 9-：通过 `new File(targetDir, candidateName).exists()` 循环检测，同样递增后缀。
- 两套逻辑封装在 `MediaSaveHelper.resolveAvailableDisplayNameByMediaStore()` 和 `resolveAvailableLegacyTargetFile()` 中。

**规则**
- 去重上限设 999，超过后直接返回失败提示，不做无限循环。
- 文件名来自调用方传入的 `displayName`（即用户可见的原始文件名），不使用缓存目录的随机文件名。

### 经验 69：Glide 网络加载图片时 previewFile 不会自动填充

**场景**
`ImageViewerActivity` 使用 Glide 从 URL 加载图片到 `PhotoView`，同时期望用户点击"保存"时能将图片写入本地。

**问题**
Glide 的 `load(url)` 只负责将图片渲染到 ImageView，不会在回调中提供本地文件引用。如果保存逻辑依赖 `previewFile != null` 来判断是否可保存，则网络加载的图片将永远提示"请等待加载完成后再保存"。

**解决方式**
在 Glide 开始加载的同一时机，并行调用 `FileRepository.download(objectName, callback)` 将文件下载到本地缓存，回调中将返回的 `File` 赋值给 `previewFile`。这样当用户点击保存时，`previewFile` 已经就绪。

**规则**
- 不要假设 Glide 加载成功等价于本地文件就绪；两者是独立路径。
- `FileRepository.download()` 本身有缓存命中逻辑（`cacheFile.exists()` 时直接返回），因此重复调用不会产生额外网络开销。

### 经验 70：PopupMenu 合并多功能菜单的重载设计模式

**场景**
三个媒体预览页面（图片/视频/文件）共用"更多"按钮，但菜单项不完全一致：视频只需"保存"，图片和文件还需"用其他应用打开"。

**问题**
如果每个 Activity 各自构建 PopupMenu，代码重复且风格不统一。

**解决方式**
在 `MediaSaveHelper` 中提供两个重载方法：
- `showSaveMenu(Context, View anchor, File sourceFile, String displayName)` — 单项菜单，只有"保存到本地"。
- `showSaveMenu(Context, View anchor, File sourceFile, String displayName, Runnable openExternalAction)` — 双项菜单，增加"用其他应用打开"，点击时执行传入的 `Runnable`。

**规则**
- 菜单项通过 `menu.add()` 动态添加，不依赖 XML menu 资源文件，减少维护成本。
- "用其他应用打开"的具体逻辑（构造 Intent、FileProvider URI、resolveMimeType）由各 Activity 自行实现，只将触发动作以 `Runnable` 传入，保持工具类的通用性。

### 经验 71：在 IDE 工作流里 `git commit -m` 多行 message 容易被静默取消，改用 `-F` 文件方案

**场景**
W2 + W3 完成后准备一次性提交 server 子仓改动。commit message 含中文标题 + 多个分组的 markdown 列表（10+ 行），用 `git commit -m "..." -m "..."` 形式提交。

**问题**
- `git commit` 命令重复出现 `Step was canceled by user`，但用户侧没看到批准弹窗
- 同样的命令换成短 message 就能成功
- 现象迷惑：到底是用户取消、IDE 弹窗渲染失败、还是 shell 解析多行 `-m` 时引号转义出问题，无法直接区分

**解决方式**
1. 把 commit message 写到 `/tmp/<name>_commit_msg.txt`
2. 用 `git commit -F /tmp/<name>_commit_msg.txt`

这样 message 任意复杂、含任意 markdown 字符都不会触发 shell 引号/换行/转义层的边界问题。

**规则**
- 任何 commit message 超过 1 行、包含中英文混排、列表符号 `-`、冒号 `:` 等特殊字符时，优先使用 `git commit -F <file>`，不要堆 `-m`
- 提交后清理临时文件不是强制的（`/tmp` 重启即清），但要避免在工作区下创建 commit message 文件意外被 add

### 经验 72：Spring 6.1+ 的 `NoResourceFoundException` 必须显式处理，否则首页一刷就刷屏 500

**场景**
启动 Web v1 server 后访问首页，浏览器自动请求 `/favicon.ico`。`static/` 下没有该资源，Spring 6.1+ 的 `ResourceHttpRequestHandler` 抛出 `NoResourceFoundException: No static resource favicon.ico`。

**问题**
- `GlobalExceptionHandler` 的 `@ExceptionHandler(Exception.class)` 兜底把它当成"服务器内部错误"，打 ERROR 级别完整堆栈，并返回 200 + `ApiResponse{code=50000}`
- 现象上看像 server 启动就崩，实际上是每次浏览器加载页面的副请求都刷一行 ERROR 堆栈
- 不止 `/favicon.ico`，所有不存在的静态资源（如 `/web/assets/<missing>.js`）都会被同样错误地兜底成 500

**解决方式**
在 `GlobalExceptionHandler` 显式加 `@ExceptionHandler(NoResourceFoundException.class)`：
- 返回 `ResponseEntity.status(HttpStatus.NOT_FOUND).build()`（HTTP 404，无 body）
- 仅以 `DEBUG` 级别记录 `ex.getResourcePath()`，避免日志噪音
- 必须放在 `Exception.class` 兜底之前，让具体异常优先匹配

**规则**
- Spring 6.1+ 项目的全局异常处理器一定要先识别 `NoResourceFoundException`，不要让它落到 `Exception.class` 兜底
- 静态资源 404 应该回 HTTP 404 原生状态码，不要包装成 ApiResponse（浏览器期望 404 而不是 200 + JSON body）
- 添加新异常处理器时，必须配套写集成测试覆盖端到端行为（路径 → 状态码 → body 不被错误包装），避免后续被 `Exception.class` 兜底回归

### 经验 73：Vite `emptyOutDir: true` + IDE 增量同步会让 Spring Boot 启动后访问 `/` 报 "静态资源未找到: index.html"

**场景**
Web v1 后端用 Spring Boot 同时承担 API 与 Web 静态资源。`vite.config.js` 把构建产物输出到 `../src/main/resources/static/web/`，并设置 `emptyOutDir: true`。日常开发流程：
1. `npm run build` 生成新产物
2. IntelliJ / `mvn process-resources` 把 `src/main/resources/` 同步到 `target/classes/`
3. Spring Boot 从 `target/classes/static/web/` 读取首页

**问题**
- `npm run build` 时 `emptyOutDir` 会先把 `src/main/resources/static/web/` 清空再写入新产物
- IDE 的增量同步并不能保证一定把"清空 + 写入"两步原子地反映到 `target/classes/`，会出现 `target/classes/static/web/` 仅剩 `assets/` 空目录、缺 `index.html` 的中间态
- 浏览器访问 `/` → `WebStaticResourceConfig` forward 到 `/index.html` → `ResourceHttpRequestHandler` 在 `classpath:/static/web/` 找不到 `index.html` → 抛 `NoResourceFoundException`
- 日志里出现 `c.f.c.exception.GlobalExceptionHandler : 静态资源未找到: index.html`，前端首页打不开

**解决方式**
在 `vite.config.js` 加 `closeBundle` 钩子，build 结束后主动把 `src/main/resources/static/web/` 镜像复制到 `target/classes/static/web/`：

```js
function syncToTargetClasses() {
  return {
    name: 'sync-to-target-classes',
    closeBundle() {
      const frontendRoot = fileURLToPath(new URL('.', import.meta.url))
      const serverRoot = resolve(frontendRoot, '..')
      const src = resolve(serverRoot, 'src/main/resources/static/web')
      const dst = resolve(serverRoot, 'target/classes/static/web')
      if (!existsSync(resolve(serverRoot, 'target/classes'))) return
      copyDirSync(src, dst)
      console.log('[vite] synced static/web → target/classes/static/web')
    }
  }
}
```

注意：
- `new URL('.', import.meta.url)` 解析得到的就是 `vite.config.js` 所在目录（即 `frontend/`），**不要再 `dirname(...)` 套一层**，否则路径会多升一级，把 dst 解析成 `/项目根/target/classes/...` 而不是 `/项目根/thunder_note_server/target/classes/...`，结果钩子虽然跑了但什么也没改
- 当 `target/classes/` 不存在（还没 mvn compile 过）时直接跳过同步，避免凭空创建空目录

**规则**
- Vite 输出到 Maven `src/main/resources/` 下时，必须考虑 IDE 同步链路的延迟与不完整问题
- 不要依赖 IDE 自动同步把 `src/main/resources/` 推到 `target/classes/`，**自己写 vite plugin 主动复制**最稳
- 改完 plugin 后必须验证：`npm run build` 输出 `[vite] synced ...`，且 `diff <(ls -1 src/main/resources/static/web/) <(ls -1 target/classes/static/web/)` 完全一致
- 路径解析靠 `import.meta.url` 时，先 `console.log` 一下确认目录层级再决定要不要 dirname

### 经验 74：在 IDE 终端用 `cat >> file <<'EOF' ... EOF` 追加多行内容也容易卡住

### 经验 77：Swift 严格并发（`-strict-concurrency=complete`）下，`static let shared` 必须 Sendable

**场景**

```swift
public final class CacheVersionMigrator {
    public static let shared = CacheVersionMigrator()
}
```
直接被编译器拒绝：`static property 'shared' is not concurrency-safe because it is not either conforming to 'Sendable' or isolated to a global actor`。

**做法**
- 类标记 `final class CacheVersionMigrator: @unchecked Sendable`；前提是内部所有 stored property 都是 `let` 且引用的对象（`UserDefaults` / `FileManager.default`）本身线程安全。

- 或把整个类改成 `actor`，调用方需要 `await`。

**规则**
- 工程开启 `complete` 严格并发时，所有跨线程被读写的全局/静态状态都必须 Sendable；不要图省事关掉 `complete`，开发后期再补成本更高。
- `@unchecked Sendable` 一定要附带"为什么手工保证安全"的注释，避免后人误以为是绿灯。

### 经验 80：iOS RefreshActor 单点去重，performer 闭包捕获要用「值类型依赖包」而不是 self

**场景**
APIClient 内部需要构造 `RefreshActor` 来做 401 单次刷新去重，第一反应是让 actor 持有 `[weak self]` 闭包并在 init 里赋给 `self.refreshActor`。在 `SWIFT_STRICT_CONCURRENCY=complete` 下编译报错：
- `passing argument of non-sendable type '() throws -> RefreshActor' into actor-isolated context may introduce data races`
- `call can throw but is not marked with 'try'`
甚至如果用懒加载 `Box` 模式（`actor RefreshActorBox` 暴露 `actor(makeIfNeeded:)`），仍要求工厂闭包 `@Sendable`，而工厂闭包又需要捕获 `APIClient self`。

**做法**
不要让 RefreshActor 的 performer 闭包捕获 `APIClient`。把刷新所需的「session / serverConfigStore / tokenAccessor / decoder / userAgent / acceptLanguage」打包成一个 `private struct RefreshDependencies: @unchecked Sendable`：
```swift
private struct RefreshDependencies: @unchecked Sendable {
    let session: URLSession
    let serverConfigStore: ServerConfigStoreProviding
    let tokenAccessor: APIClient.TokenAccessor
    let decoder: JSONDecoder
    let userAgent: String
    let acceptLanguage: String
    func performRefresh() async throws -> LoginResponse { /* 直接发请求 */ }
}
```
然后在 `APIClient.init` 里：
```swift
let deps = RefreshDependencies(...)
self.refreshActor = RefreshActor { try await deps.performRefresh() }
```
performer 闭包只捕获 `deps` 这个值类型，没有引用循环、不需要 `self`、自然 Sendable。

**规则**
- 严格并发下，actor 的 performer 闭包优先用「值类型依赖包」捕获，不要捕获 `self`。
- 既能避开 `@Sendable` 上的引用循环风险，又能让 RefreshActor 在 init 里就准备好（不需要懒加载 box）。
- 同样思路适用于其他「需要长生命周期 actor + 一组只读依赖」的场景，比如 BackgroundSyncActor、UploadActor 等。

### 经验 81：测试用 `MockURLProtocol` 共享状态在 Swift 6 下需要 `nonisolated(unsafe)`

**场景**
APIClient 单测要注入 mock，标准做法是写一个 `URLProtocol` 子类，把 handler 存到 `static var _handler`。Swift 6 / `SWIFT_STRICT_CONCURRENCY=complete` 下报：
```
Static property '_handler' is not concurrency-safe because it is non-isolated global shared mutable state; this is an error in Swift 6
```
对 `_requestLog` 这样的 `static var [URLRequest]` 同样报错。

**做法**
- 真实的并发安全已经由一个内部 `DispatchQueue` 串行化 `get/set` 提供。
- 给 storage 字段标 `nonisolated(unsafe)`，明确告诉编译器这一份共享状态由别处保证安全：
```swift
final class MockURLProtocol: URLProtocol, @unchecked Sendable {
    static let queue = DispatchQueue(label: "tn.tests.mockurlprotocol")
    nonisolated(unsafe) private static var _handler: Handler?
    nonisolated(unsafe) private static var _requestLog: [URLRequest] = []

    static var handler: Handler? {
        get { queue.sync { _handler } }
        set { queue.sync { _handler = newValue } }
    }
}
```
- `Handler` 类型本身要是 `@Sendable (URLRequest) throws -> (HTTPURLResponse, Data)`。
- 测试里凡是要在 mock handler 闭包里写跨调用计数器，不要捕获 `var` 变量；定义一个 `final class AtomicCounters: @unchecked Sendable`，内部用 `NSLock` 同步即可。

**规则**
- Swift 6 全严格并发开关下，`static var` 的可变全局状态要么搬到 actor，要么标 `nonisolated(unsafe)` + 自带同步原语。
- 测试里所有跨闭包共享的可变量都改成 `final class @unchecked Sendable + NSLock`，不要用 `var x = 0; closure { x += 1 }` 老套路，编译会直接拒绝。
- mock 文件必须 `@testable import ThunderNote`，否则 host App 内的内部协议（如 `ServerConfigStoreProviding`）在测试 target 看不到。

### 经验 82：iOS 严格并发下 `static let shared` 单例除了 `@unchecked Sendable`，还要避免 `[weak self]` 跨 init 闭包

**场景**
`AppDependencies` 这种顶层 DI 容器经常会写：
```swift
let accessor = DefaultTokenAccessor(
    tokenStore: tokenStore,
    onSessionUpdated: { [weak session] response in
        guard let session else { return }
        await MainActor.run { session.signIn(response) }
    }
)
```
在严格并发下，`AuthSession` 是 `@MainActor` 的 ObservableObject，但 `onSessionUpdated` 是 `@Sendable (LoginResponse) async -> Void`。需要在闭包内部显式 `await MainActor.run { ... }` 才能调用 `signIn`，不能直接 `session.signIn(response)`。

**做法**
- DI 容器持有的回调闭包参数类型一律 `@Sendable async -> Void`。
- 闭包里访问 `@MainActor` 的对象，先 `await MainActor.run { ... }`。
- 闭包外部捕获 `[weak xxx]` 时，被捕获对象本身要是 class（`AuthSession` 是 `final class`），不要捕 struct。

**规则**
- Sendable 闭包 + MainActor 对象的标准写法：捕获弱引用 → 闭包内 `await MainActor.run { ... }` 调真正的 main actor 方法。
- 不要让 `@Sendable` 闭包同步访问 main actor 状态，编译器一定会拒绝。

**规则**
- iOS 16 deployment target 下默认用 `targeted`；不要把项目卡在 `complete` 然后被某个孤立的系统类型导致整条链路寸步难行。
- 写到 `targeted` 的同时，要在 project.yml 里加注释说明触发原因 + 升级路径，避免后续维护者误以为是疏忽。
- 自己的 ViewModel / Repository 仍按 `@MainActor` / `actor` / `Sendable` 严格写，不要把整个项目的并发卫生让出去。

### 经验 84：iOS 16 `PhotosPickerItem` 的安全使用模式

**场景**
`PhotosPicker(selection:)` 绑到 `@Published var selectedItem: PhotosPickerItem?`，然后异步读 `item.loadTransferable(type: Data.self)`。
- iOS 16 SDK 没把 `PhotosPickerItem` 标 `Sendable`，跨 await 时编译器会拒绝。
- iOS 17 SDK 把它标了 `Sendable`，相同代码就能编过——只看部署目标。

**做法**
封装一个 helper 类：

```swift
final class PhotosPickerHelper: ObservableObject, @unchecked Sendable {
    @Published var selectedItem: PhotosPickerItem? = nil

    func loadLocalURL(suggestedExtension fallback: String) async -> URL? {
        guard let item = selectedItem else { return nil }
        let ext = fileExtension(for: item) ?? fallback // 同步先取扩展名
        let data = try? await item.loadTransferable(type: Data.self)
        guard let data else { return nil }
        let url = FileManager.default.temporaryDirectory
            .appendingPathComponent("tn-picked-\(UUID().uuidString).\(ext)")
        try? data.write(to: url, options: .atomic)
        return url
    }
}
```

要点：
- helper 本身打 `@unchecked Sendable`，让 Swift 严格并发对系统未标 Sendable 的字段闭嘴。
- 实际访问全部走 SwiftUI `@StateObject`，从来不会跨 actor。
- 不要给 helper 加 `@MainActor` —— 跟 `loadTransferable` 的 `nonisolated async` 签名打架。

**规则**
- 在 iOS 16 deployment target 下处理 `PhotosPickerItem` / `Transferable` 等不带 Sendable 的系统类型，优先封装 `@unchecked Sendable` 的 helper 类，而不是在调用点逐个 `@unchecked Sendable struct`。
- 把扩展名 / 文件名等本地纯计算放在 `await` 之前完成，减少跨 actor 边界 carry 的状态。

### 经验 85：Swift 严格并发下 Timer 闭包里 `[weak self]` 的安全跳板

**场景**
iOS 端 D2-I3-11 录音 helper 在 `AVAudioRecorder` 上挂一个 100ms 的 `Timer`，要在 callback 里更新 `@MainActor` 隔离的 `levels` / `elapsed`：

```swift
@MainActor
final class ChatRecordingHelper: NSObject, ObservableObject {
    private func startSampling() {

    }
}
```

```
error: reference to captured var 'self' in concurrently-executing code
```

原因：`[weak self]` 是把 `self` 捕获成 `var`（这是 Swift weak capture 的标配）。再把它带进 `Task { @MainActor }` 时 Swift 把 Task 闭包视为「并发执行」上下文，捕获**外层的 var**就触发严格检查。

**做法**
在 Timer 闭包内先 `let` 重绑一次再传入 Task：

```swift
let timer = Timer(timeInterval: 0.1, repeats: true) { [weak self] _ in
    let weakSelf = self        // immutable rebind
    Task { @MainActor in
        weakSelf?.tick()
    }
}
```

或者更激进的：把回调写成 `nonisolated static` 函数接 `weakSelf` 参数，从而完全脱离闭包捕获判定。

**规则**
- 不要直接在 `Task { @MainActor }` 里访问 `[weak self]` 的 `self?`；先 `let weakSelf = self` 拿稳定值。
- 通用模式：`Timer` / `DispatchSourceTimer` / 任何 `@Sendable` 闭包 → Task hop 时，遇到 `var` 捕获就先 `let` 兜一层。
- 严格并发（`SWIFT_STRICT_CONCURRENCY=targeted` 及以上）下，遇到 `reference to captured var 'self' in concurrently-executing code` 这条报错，第一时间检查是否是 weak-self → Task 的链路。

### 经验 86：iOS `XCTest` 闭包里捕获 var 同样会触发严格并发报错

**场景**
iOS 端写 `AuthenticatedImageLoader` 单测：

```swift
var hitCount = 0
MockURLProtocol.handler = { request in
    hitCount += 1                                       // ← ❌
    return (HTTPURLResponse.make(...), Data())
}
```

`MockURLProtocol.handler` 是 `@Sendable` 闭包；测试里捕获到的 `var hitCount` 会被严格并发判为「捕获的 var 在并发上下文里被 mutate」。

**做法**
把 `var` 替换成一个线程安全的小封装：

```swift
private final class HitCounter: @unchecked Sendable {
    private let lock = NSLock()
    private var _value = 0
    func increment() { lock.lock(); defer { lock.unlock() }; _value += 1 }
    var value: Int  { lock.lock(); defer { lock.unlock() }; return _value }
}
let counter = HitCounter()
MockURLProtocol.handler = { _ in counter.increment(); return (..., Data()) }
XCTAssertEqual(counter.value, 1)
```

同理 capture string / dict 的场景做成 `AuthHeaderProbe` 一类小类，统一 `NSLock` 包内部状态。

**规则**
- 不要在 `@Sendable` handler 闭包里直接捕获 `var` 用作计数器 / probe；用一个 `@unchecked Sendable` + `NSLock` 的 helper 类。
- `XCTestCase` 的 `var` 实例属性同样不安全；如果一定要在并发上下文写，包成 helper 类。
- 这条与经验 85 配合：严格并发报「captured var」时，要么 `let` 重绑，要么换 helper 类。

### 经验 87：iOS 模拟器/未签名构建下 Keychain 静默失败 `errSecMissingEntitlement (-34018)`

**现象**
- 用 `CODE_SIGNING_ALLOWED=NO` 在模拟器上构建 ThunderNote，登录后立刻闪回登录页；后端日志显示 `/api/auth/login 200` 成功，但紧随其后的 `/api/sync/bootstrap`、`/api/flash-notes/list` 等全部 401，`Authorization` 头为空。
- 抓取 `xcrun simctl spawn booted log stream --predicate 'eventMessage CONTAINS "TN-DIAG"'` 可见：`Keychain SecItemUpdate FAILED key=tn.auth.access_token status=-34018`。

**根因**
- 模拟器 / `CODE_SIGNING_ALLOWED=NO` 构建产物没有 `application-identifier` / `keychain-access-groups` entitlement，`SecItemAdd/Update/CopyMatching` 全部返回 `-34018 errSecMissingEntitlement`。
- 原 `KeychainTokenStore.writeString` 不检查返回码，写入静默失败 → `loadAccessToken()` 永远 nil → APIClient 401 → 刷新链路读不到 refresh token → `clearSession` → `forceUnauthenticated` → 退回登录页。
- `KeychainGestureLockStore` 有同款盲点，手势锁看似设置成功，下次启动 `isEnabled` 永返 false。

**解决方式**
- 推荐：Xcode → Signing & Capabilities 挂任意 Apple ID 团队（免费 Personal Team 即可），把 Team ID 写进 `project.yml` 的 `DEVELOPMENT_TEAM`，使 `xcodegen` 重新生成项目后仍保留签名配置。模拟器与真机均走正常 Keychain 路径。
- 兜底：`KeychainTokenStore` / `KeychainGestureLockStore` 加 UserDefaults 兜底；检测到 `errSecMissingEntitlement` 后置 `useFallback=true`，并把 sentinel key 写进 UserDefaults，下次启动延续兜底，避免一个会话内 Keychain / UserDefaults 来回切读到旧值。生产真机带签名不会激活兜底，安全等级不变。

**后续规则**
- iOS 任何 `SecItem*` 调用必须检查返回码，至少要 `NSLog` 出 status，绝不允许静默失败。
- 新建 Keychain-backed store 时，沿用 `KeychainTokenStore` / `KeychainGestureLockStore` 的 UserDefaults fallback 模式，让无签名构建也能跑通主链路。
- CI 上不带签名时，token / 手势锁等敏感数据走 UserDefaults 兜底；不要据此推断生产安全等级。
- 排查"登录后闪回登录页"或"手势锁设了不生效"类问题时，第一步看 `[TN-DIAG]` 是否出现 `Keychain ... missing-entitlement`。

### 经验 88：iOS `QLPreviewController` 对 EPUB 可能只显示元数据不渲染正文

**现象**
- iOS 客户端点击 `.epub` 文件后，预览页能打开，顶部/内容区显示"EPUB 出版物"和文件大小，但不显示书籍正文。

**后续规则**
- 对"QuickLook 能识别文件类型但不显示内容"的格式，不要只判断为"下载成功"；应按格式单独验证正文是否可阅读。
- 对 ZIP 类容器（EPUB、Office OpenXML 等）做任何解包时，必须先做路径归一化与根目录约束，再写入磁盘。

### 经验 89：iOS 自托管服务器历史应独立于当前服务器选择

**现象**
- 用户安装 / 重装后希望复用之前输入过的自托管服务器，不想每次重新手输。
- 早期实现只保存"当前自托管 URL"，切回官方服务器时会移除当前 URL；如果历史列表与当前 URL 混用，用户切回官方后就失去可复用入口。

**解决方式**
- `ServerConfigStore` 分开维护两个概念：
  - `tn.server.self_hosted_url`：当前正在使用的自托管 URL，仅在 `mode=self_hosted` 时生效。
  - `tn.server.self_hosted_history`：历史自托管 URL 列表，切回官方不清理。

- `useOfficial()` 只切 mode 并清当前 URL，不删除历史列表。
- `deleteSelfHostedHistory(url:)` 只删除指定历史项；如果删除的是当前正在使用的自托管地址，则同时切回官方并触发冷重置。

**后续规则**
- 服务器切换相关能力要区分"当前生效配置"和"历史选择项"，不要为了退出当前环境而清掉用户的历史输入。
- 历史服务器条目只保存 base URL，不保存用户名、token、密码等敏感信息；站点切换仍必须清登录态。

### 经验 93：EPUB 解析兼容性要覆盖 URL 编码路径、fragment 和 DOCTYPE

**现象**
- Android `.epub` 已经进入 `FilePreviewActivity` 后，仍提示"EPUB 预览失败，已为你保留外部打开"。
- JVM 单测通过，但安装到模拟器后 instrumentation 测试仍复现失败。

**根因**
- Android 设备端 `DocumentBuilderFactory.setXIncludeAware(false)` 可能抛出 `UnsupportedOperationException: This parser does not support specification "Unknown" version "0.0"`；旧实现直接调用该方法，导致 `EpubDocument.prepare()` 在设备端失败。
- 真实 EPUB 的 `container.xml` / OPF 中可能出现 `full-path="OPS/package%20file.opf#opf"`、章节 `href="Text/chapter%201.xhtml#start"` 或资源 `src="../Images/cover%20image.png#cover"`。
- 旧版解析直接把这些 href 当文件路径使用，未去掉 fragment/query，也未对 `%20` 等 URL 编码做安全解码，导致解包后文件存在但解析层找不到。
- 部分 EPUB XML 包含合法 DOCTYPE；强制禁 DOCTYPE 会直接解析失败，但完全放开又有 XXE 风险。

**解决方式**
- `setXIncludeAware(false)` 和 `setExpandEntityReferences(false)` 改为 `setXIncludeAwareIfSupported()` / `setExpandEntityReferencesIfSupported()`，在 Android parser 不支持时忽略；安全主防线仍依赖禁外部实体、禁外部 DTD/schema 和空 EntityResolver。
- 对 OPF 路径、章节 href、资源 src/href 统一先去掉 fragment/query，再做 `%xx` 解码，并继续用 canonical path 校验必须留在 EPUB 缓存根目录下。
- XML 解析优先禁 DOCTYPE；若失败，再读取 UTF-8 内容剥离 DOCTYPE 后重试，同时保持 `external-general-entities` / `external-parameter-entities` / 外部 DTD/schema 禁用，并设置空 EntityResolver。
- 新增 `EpubDocumentTest.prepare_allowsDoctypeWithoutLoadingExternalEntities` 和 `prepare_resolvesEncodedHrefAndFragment`，覆盖带 DOCTYPE 与 URL 编码路径场景；新增 `FilePreviewActivityTest` instrumentation 测试，直接在模拟器中从应用进程启动 `FilePreviewActivity`，确认 EPUB WebView 可见、错误提示隐藏。

**后续规则**
- ZIP 容器格式里 manifest 引用通常是 URL 语义，不等同于文件系统路径；解析前必须处理 fragment/query 和 URL 编码，再进入安全路径校验。
- 兼容 EPUB DOCTYPE 时，只能剥离或禁外部实体，不能直接放开外部 DTD / 外部实体加载。
- 涉及 Android 平台 XML parser / WebView 的功能，不能只依赖 JVM 单测；至少补一个 instrumentation 测试验证设备端运行时行为。

### 经验 94：服务器切换后首次登录要重点检查后台 sync 回调线程

**现象**
- Android 切换服务器后，第一次登录会闪退。
- 初看窗口日志只显示进程死亡 / `signal 9 (Killed)`，普通 `grep FATAL EXCEPTION` 可能被截断遗漏真实 Java 堆栈。

**根因**
- 真实堆栈来自 crash buffer：`FATAL EXCEPTION: pool-21-thread-1`，异常为 `IllegalStateException: Cannot invoke setValue on a background thread`。
- 登录成功后 `PendingRecoveryWorker` / `SyncRepositoryImpl.pullAndRefreshLocal()` 会在后台线程执行 sync pull，成功回调里触发 `flashNoteRepository.refresh()` / `collectionRepository.refresh()` / `favoriteRepository.refresh()`。
- `CollectionRepositoryImpl.refresh()` 使用共享 `RepositoryStateStore.setLoading()` 更新 loading；旧实现内部直接 `MutableLiveData.setValue()`，后台线程调用时 Android 直接抛异常并杀进程。

**解决方式**
- `RepositoryStateStore` 统一封装 LiveData 更新：主线程用 `setValue()`，后台线程用 `postValue()`。
- 新增 `RepositoryStateStoreTest.updates_doNotThrowFromBackgroundThread`，覆盖后台线程调用 `setLoading()` / `setError()` / `clearError()` 不再抛异常。
- 验证 `CollectionRepositoryImplTest`、`FavoriteRepositoryImplTest`，确保共享状态容器修改不破坏现有 repository 行为。

**后续规则**
- Android repository / sync / WorkManager 链路中的 LiveData 状态更新必须考虑回调线程，不允许在共享状态容器里直接无条件 `setValue()`。
- 遇到进程死亡但常规日志只看到 `WINDOW DIED` / `signal 9` 时，要继续查 `adb logcat -b crash` 或按 PID 抓完整日志，避免误判为系统 kill 或半登录态问题。

### 经验 95：Android 11+ 包可见性会让外部打开静默失败

**现象**
- Android 客户端点击 PDF / .py / Office 文件气泡，弹"未找到可打开该文件的应用"，连系统选择器都不弹。
- 设备明明装了 PDF 阅读器 / WPS / Office 等可处理 ACTION_VIEW 的应用。

**根因**
- `targetSdk = 34`，Android 11+ 启用包可见性策略；`AndroidManifest.xml` 缺 `<queries>` 时，`PackageManager.queryIntentActivities()` / `intent.resolveActivity()` 会被过滤成空，即便应用真实存在。
- `MessageAdapter.openFileWithExternalApp` 用 `intent.resolveActivity(...) == null` 做兜底判断，因此被误判成"未找到"，直接 toast 而不调用 `startActivity`。
- 同时 `openCachedFile` 解析扩展名只读 `message.fileName`；当来源是 SAF/共享/历史消息且 `fileName` 缺扩展时，PDF/py 也会跌到外部打开分支，叠加上面的可见性问题就一起报"未找到"。

**解决方式**
- `AndroidManifest.xml` 顶层补 `<queries>`：声明 `android.intent.action.VIEW` 与 `android.intent.action.SEND`，让本应用能看到处理这两类 intent 的外部应用。
- `MessageAdapter` 新增 `resolveEffectiveExtension(fileName, mediaUrl, cachedFileName)`：扩展名按 fileName → mediaUrl → 缓存文件名顺序回退，避免 fileName 缺扩展时 PDF/py 走外部打开。
- 配套测试 `MessageAdapterTest.resolveEffectiveExtension_prefersFileNameThenMediaUrlThenCache` 覆盖三层 fallback 与全空场景。

**后续规则**
- 任何走 `Intent.ACTION_VIEW` / `ACTION_SEND` + `resolveActivity` 的逻辑，都必须先确认 `<queries>` 已经声明对应 intent，否则 Android 11+ 上必定误判。
- 文件类逻辑解析扩展名时，优先读 `message.fileName`，但必须保留 `mediaUrl` / 缓存文件名兜底，不要假设服务器或客户端总是写入完整带扩展的 fileName。

### 经验 96：Office 文档应用内预览可用原生 ZIP/XML 解析，无需 Apache POI

**现象**
- 需要 Android 端直接预览 Word/Excel/PPT，不想依赖外部应用或重型 SDK。

**根因**
- `.docx` / `.xlsx` / `.pptx` 本质是 ZIP 压缩包，内部是标准 XML。
- Apache POI 在 Android 上体积大（~10MB+），且依赖 `javax.xml` 可能与 Android 内置实现冲突。

**解决方式**
- 新增 `OfficeDocumentParser`：纯 `ZipInputStream` + `DocumentBuilderFactory` 解析，零额外依赖。
  - Word：读 `word/document.xml`，提取 `<w:t>` 文本 + `<w:rPr>` 格式（粗体/斜体/下划线）+ `<w:pStyle>` 标题层级。
  - Excel：读 `xl/sharedStrings.xml` + `xl/worksheets/sheet1.xml`，生成 HTML `<table>`。
  - PPT：读 `ppt/presentation.xml` 获取 slide 列表 → `ppt/_rels/presentation.xml.rels` 解析关系 → `ppt/slides/slideN.xml` 提取 `<a:t>` 文本。
- 生成自包含 HTML，在 `WebView` 中渲染（复用 EPUB 预览的 WebView）。
- WebView 安全配置：禁用 JS、文件访问、内容访问，拦截所有 URL 导航。
- XML 解析安全加固：禁用 DOCTYPE、外部实体、外部 DTD。

**后续规则**
- Office Open XML 格式（.docx/.xlsx/.pptx）优先用原生 ZIP/XML 解析，避免引入 Apache POI。
- 旧二进制格式（.doc/.xls/.ppt）暂不支持应用内预览，走外部打开。
- WebView 渲染用户文件内容时必须锁定 JS/文件访问/导航，防止 XSS 或文件泄露。

### 经验 97：refresh token 不能在普通认证请求中静默轮换

**现象**
- Android 客户端登录后一段时间重新打开，接口先报 401，随后跳回登录页。
- 启动页即使允许 refresh token 存在时恢复会话，后续自动 refresh 仍可能失败并清登录态。

**根因**
- 后端 `JwtAuthenticationFilter` 在普通 access token 认证成功后，会按活跃度在 Redis 中静默生成并覆盖新的 refresh token。
- 该轮换发生在普通业务响应里，客户端没有收到新的 refresh token，仍保存旧 refresh token。
- 当 access token 过期后，Android `TokenAuthenticator` 用旧 refresh token 调 `/api/auth/refresh`，服务端与 Redis 中的新 token 不匹配，返回未授权，客户端清 token 回登录。
- Android 旧逻辑在 refresh 请求遇到异常或临时失败时也会直接 `clearTokens()`，会把可恢复的网络 / 5xx 问题放大成强制登录。

**解决方式**
- 后端移除 `JwtAuthenticationFilter` 中普通认证请求的静默 refresh token 轮换，只在显式 `/api/auth/refresh` 时返回新 token 给客户端保存。
- Android `TokenAuthenticator` 调整为仅在 refresh 响应明确为 HTTP 401/403 或业务码 40100/40300 时清 token；临时 5xx、网络异常、响应解析异常不再直接清 token。
- 新增 `JwtAuthenticationFilterTest.authenticatedAccessToken_doesNotRotateRefreshTokenSilently` 锁定普通请求不再轮换。
- 新增 `TokenAuthenticatorTest` 覆盖 refresh 500 不清 token、refresh 401 才清 token。

**后续规则**
- 任何 refresh token 轮换都必须是显式协议的一部分，并把新 token 返回给客户端持久化；不要在过滤器 / 拦截器里静默替换服务端 token 状态。
- 客户端自动 refresh 失败要区分“凭证确定无效”和“临时不可用”；只有前者才能清本地登录态。
- 认证链路变更必须同时补服务端行为测试和客户端 authenticator / interceptor 回归测试。

### 经验 98：Android 离线待发消息要恢复中断状态并保护本地确认消息

**现象**
- Android 离线发送一条闪记消息后，消息发送失败。
- 恢复在线后进入待同步列表点击同步，条目长期停留在“发送中”。
- 在闪记消息页点重发也无法真正同步。
- 此时新发出的消息过一段时间会在 App 本地消失，但服务端实际仍然存在。

**根因**
- `PendingMessageDispatcher` 只会调度 `QUEUED/FAILED`，而离线发送过程中断后可能残留 `SENDING/UPLOADING/PROCESSING/UPLOADED`。
- 这些“飞行中”状态虽然被待同步列表统计出来，但旧的手动同步 / 会话重发 / 单条重发路径没有先调用 `recoverInterruptedMessages()`，因此 dispatcher 认为不可调度。
- 若 dispatcher 内存里的 `dispatchInProgress` 已经停在 `true`，即使数据库状态后续被重置，新的调度也会被忙碌标记挡掉。
- 另一方面，消息页第一页远端刷新会 `clearConversation()` 再写入当前页结果；如果本地已有服务端确认消息但当前分页没有返回该条，会被本地清掉，造成“App 消失但服务端还有”。

**解决方式**
- 单条重发允许 `QUEUED/FAILED/PROCESSING/UPLOADING/UPLOADED/SENDING` 都进入重试路径。
- `PendingMessageDispatcher` 新增恢复调度入口：先重置 `dispatchInProgress=false`，再恢复中断状态并调度当前会话或全部 pending。
- `MessageRepositoryImpl.retryPendingForCurrentConversation()` / `retryAllPendingMessages()` 改走恢复调度入口，手动同步和会话页重发都能处理残留“发送中”。
- `MessageRepositoryMergeHelper` 只把 `PROCESSING/UPLOADING/UPLOADED/SENDING` 标成 uploading；`QUEUED` 不再禁用重发按钮。
- `MessageRepositoryPersistenceHelper.persistRemoteMessages(..., replaceConversation=true)` 清会话前保留本地已有、但当前远端页未返回的确认消息，避免分页刷新误删本地服务端消息。
- 新增 `MessageRepositoryImplTest` 覆盖：`SENDING` 可重试、`retryAllPendingMessages()` 会恢复中断状态、`QUEUED` pending 不再显示 uploading、第一页刷新保留本地确认消息。

**后续规则**
- 待同步列表里展示的所有状态，都必须有对应恢复 / 重试路径；不能只展示 `SENDING` 但 dispatcher 不调度。
- 手动同步、后台恢复、会话页重发三条入口必须共享“恢复中断状态 + 重置调度器忙碌标记”的语义。
- 用分页结果刷新本地 Room 时，不要把“当前页未返回”直接等同于“服务端已删除”；删除语义必须由明确删除接口或 tombstone 驱动。

### 经验 99：跨端消息类型字段要区分“会话归属”和“渲染类型”

**现象**
- Web 端发送消息后，Android 在“我的/闪记列表”里点击同步，列表预览能看到最后一条消息已经更新。
- 但进入对应闪记聊天页，看不到这条新消息；退出 App 再进入后才显示。
- Android 端发送的纯文字消息，在 Web 端被渲染成“图标 + 附件 + 文字”，而不是普通文字气泡。

**根因**
- 后端闪记消息会同时带 `flashNoteId` 和 `receiverId`；Android `SyncRepositoryImpl.toMessageLocalEntity()` 通过 `ConversationKeyUtil.resolve(flashNoteId, receiverId)` 计算本地会话 key。
- 旧 `ConversationKeyUtil.resolve()` 优先使用 `peerUserId/receiverId`，导致带 `flashNoteId` 的闪记消息被落到联系人会话 key，而不是闪记会话 key。
- 因此同步后闪记列表预览由 `FlashNoteRepository.refresh()` 更新了，但消息 Room 记录在错误 conversationKey 下，闪记聊天页的 `MessageRepositoryImpl` 看不到。
- Web `MessageBubble` 旧逻辑只要 `mediaType` 非空就当媒体消息；Android 文字消息会显式带 `mediaType=TEXT`，于是被误判为附件。

**解决方式**
- Android `ConversationKeyUtil.resolve()` 改为优先使用 `flashNoteId`，只有没有闪记 ID 时才按联系人会话归属。
- 新增 `SyncRepositoryImplTest.pull_usesFlashNoteConversationKeyWhenFlashNoteMessageAlsoHasReceiverId`，锁定闪记消息同步落库 key。
- Web `MessageBubble` 的 `isMedia` 明确排除 `mediaType=TEXT`，只把真正媒体/文件类型交给 `MediaPreview`。
- 新增 `MessageBubble.test.js` 覆盖 `TEXT` 类型消息应渲染为纯文本。

**后续规则**
- 会话归属优先级：只要消息有有效 `flashNoteId`，就属于闪记会话；联系人会话只用于没有 `flashNoteId`、按双方用户 ID 对话的消息。
- 渲染类型判断不能简单使用“mediaType 非空”；`TEXT` 是文本类型，不是媒体/附件类型。
- 任何跨端新增或调整消息字段时，至少同时覆盖 Android 落库会话 key 与 Web 气泡渲染两类回归。

### 经验 100：Web 构建后 IDE 启动要同时支持 classpath 与开发期静态目录

**现象**
- 后端启动后访问 Web 页面失败，接口返回“静态资源未找到: index.html”。
- `src/main/resources/static/web/index.html` 实际存在，但 `target/classes/static/web/index.html` 不存在。

**根因**
- Spring Boot 运行时默认从 classpath 读取 `classpath:/static/web/`。
- Vite 构建产物写到 `src/main/resources/static/web/`，但 IDE / DevTools 的增量资源同步不一定会把新产物同步到 `target/classes/static/web/`。
- 如果此时后端从已有 `target/classes` classpath 启动，`WebStaticResourceConfig` 只看 classpath，就会找不到 `index.html`。
- 旧 SPA fallback 直接用 `ClassPathResource("/static/web/index.html")`，即使资源 handler 增加其他 location，也无法从开发期文件目录 fallback。

**解决方式**
- `WebStaticResourceConfig` 的 resource locations 同时配置 `classpath:/static/web/` 和 `file:src/main/resources/static/web/`。
- `SpaFallbackResolver` fallback 时使用当前 location 下的 `index.html`，而不是硬编码 `ClassPathResource`。
- `WebStaticResourceIntegrationTest` 覆盖 `/index.html` 和 SPA route fallback。

**后续规则**
- Web v1 构建产物由 Spring Boot 承载时，本地开发要兼容 `target/classes` 与 `src/main/resources` 两种加载路径。
- 静态资源 resolver 的 fallback 不要硬编码 classpath；否则新增 file location 也不会生效。
- 遇到“src 有 index.html，但运行时报找不到”时，优先检查 `target/classes/static/web/` 与 resource handler locations。

### 经验 101：Refresh token “未到期但 expired”要先查 Redis 会话覆盖

**现象**
- Android 客户端登录不到一天再次请求接口触发 401。
- 后端日志报：`业务异常: Refresh token has expired`。
- 表面看像 refresh token 时间没到却过期。

**根因**
- 该错误并不只代表 JWT `exp` 到期；在后端 `AuthServiceImpl.refreshToken()` 中，它也代表 Redis 里的 refresh 会话 key 缺失或不匹配。
- 旧实现把 refresh token 存在单用户 key：`auth:refresh:{userId}`。
- 同一账号在 Web 与 Android 多端登录/刷新时，后登录或后刷新的端会覆盖这个 key。
- 另一个端手里持有的 refresh JWT 仍未过期，但 Redis 已不再保存它，于是刷新时报 `Refresh token has expired`。

**解决方式**
- refresh 会话改为按 token 指纹独立存储：`auth:refresh:{userId}:{sha256(refreshToken)}`，value 存 userId，不在 Redis key 中存明文 token。
- session start 同步改为 token 级 key：`auth:refresh:session:{userId}:{sha256(refreshToken)}`，保证多端独立维护最大会话时长。
- refresh 成功时只删除当前旧 token 的会话 key，再写入新的 token-scoped key。
- 保留旧 `auth:refresh:{userId}` / `auth:session:start:{userId}` 兼容读取，旧单会话 token 首次刷新后迁移到新 key。
- logout 按用户清理 token-scoped refresh/session key，并删除旧 key，保持“显式登出清该用户所有 refresh 会话”的当前安全语义。
- 新增 `AuthServiceImplTest` 覆盖多次登录不覆盖旧 refresh 会话、合法 refresh 轮换、旧 key 迁移和 logout 清理。

**后续规则**
- 不要把 “Refresh token has expired” 直接判断成时间 TTL 问题；先查 Redis key 是否被多端登录/刷新覆盖。
- 支持多端登录时，refresh token 服务端状态必须以 token/session 为粒度，不能只以 userId 为粒度。
- Redis key 不应包含 refresh token 明文；需要定位单个 token 时使用 SHA-256 指纹或其他不可逆摘要。
