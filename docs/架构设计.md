# 架构设计

## 文档定位
本文档同时描述**当前态架构**与**目标态架构**。阅读时不要把目标态误当成已实现。

## 当前态架构
### 仓库结构
- 后端：`thunder-note-server/`
- Android：`thunder-note-android/`
- 原型：`thunder-note-prototype.html`
- 文档：`docs/`

### 当前系统形态
- 服务端为 Spring Boot 模块化分包后端
- 客户端当前只有 Android 真正落地，且当前主模块已经是 Java 客户端
- Web、iOS，管理后台仍属于规划能力；其中 Web 用户端已明确后续写入 `thunder_note_server/` 并由同一个 Spring Boot 服务托管页面
- HTML 原型承担交互验证角色，不代表生产实现

### 当前后端模块
| 模块 | 状态 | 说明 |
|------|------|------|
| auth | 已实现基础 | 注册、登录、刷新、登出 |
| user | 已实现基础 | 用户资料查看/修改 |
| flashnote | 已实现基础 | 闪记基础 CRUD |
| message | 已实现基础 | 基础消息列表/发送 + SSE stream，当前已补 `flash_note_id` / `role` 支撑 Android 闪记内对话 |
| collection | 已实现基础 | 合集基础 CRUD |
| file | 已实现基础 | 上传、下载 |
| sync | 已实现基础 | controller 已有基础接口，Android 已接通，push 可处理 notes / collections / messages / favorites |
| favorite | 已实现基础 | 当前提供消息收藏列表/新增/删除最小闭环 |
| search | 未实现 | 仅设计存在 |
| admin | 未实现 | 仅设计存在 |

### 当前 Web 状态
- 当前仓库尚无真实 Web 用户端代码。
- 后续 Web 用户端按计划落在 `thunder_note_server/`，服务端继续作为模块化单体，同时承担 Android API 与 Web 页面承载。
- Web 首版应复用当前 `/api/...` 契约；静态资源路由、前端路由 fallback 与 `/api/**` 鉴权边界需要在实现前单独设计。

### 当前客户端架构
- 当前 Android Java 客户端以 Activity / Fragment + ViewBinding + ViewModel 为主
- 当前 Java 网络基础层使用 Retrofit + OkHttp
- 当前 Java Token 通过 `EncryptedSharedPreferences` 保存
- 当前 Java `auth / flashnote / chat` 已有可编译主链
- 当前 Java `favorite` 已接真实收藏数据；`collection` 已接真实数据；`profile` 当前提供 sync / file / logout 基础操作面

## 目标态架构
### 目标系统范围
- 后端 + Android + Web + iOS + 管理后台
- 多端共享统一的数据模型与同步协议
- 搜索、收藏，系统信息、后台管理等扩展模块逐步补齐

### 目标设计原则
- 服务端继续保持模块化单体方向
- 新 Android 客户端统一按可维护的 Java 分层架构组织
- Web 用户端首期采用后端同仓同服务承载，优先保证与 Android 共享 API 契约，而不是另起一套服务端
- 当前态、目标态、原型设计必须分文档或分章节明确标注

## 已知架构漂移
- 旧文档中 MySQL、React、Elasticsearch、WebSocket 等表述已经不再代表当前主线方案
- 当前 API 实际路径为 `/api/...`，不是 `/api/v1/...`
- 当前真实仓库并没有 Web、iOS、admin 代码目录；Web 已进入后续计划，但仍未落地为真实代码

## 维护规则
- 当前态架构必须以代码、配置、迁移脚本为准
- 目标态架构可以保留，但必须明确标注"尚未实现"
- 当旧设计整体失真时，优先重写当前态章节，不在旧文上做碎片式修补
