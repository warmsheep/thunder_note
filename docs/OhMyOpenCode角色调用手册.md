# 闪记项目 - Oh My OpenCode 角色调用手册

> 适用对象：项目负责人本人  
> 适用项目：闪记（Thunder Note）  
> 目标：在当前项目中，明确什么时候调用 `Sisyphus`、`Hephaestus`、`Prometheus`、`Atlas`，以及辅助角色该如何配合使用。

---

## 一、先记住这一句

在这个项目里，我默认按下面这条链路使用代理：

`Prometheus` 想清楚 -> `Atlas` 按计划推进 -> `Sisyphus` 直接执行中等到复杂任务 -> `Hephaestus` 攻坚难题 -> `Oracle / Librarian / Explore` 作为专项辅助

如果只是小改动，不需要完整编排，直接让当前主代理处理即可。

---

## 二、角色定位

### 2.1 Prometheus

`Prometheus` 是规划者，不是主执行者。

适合做的事：

- 澄清需求边界
- 识别遗漏和风险
- 拆分实施步骤
- 定义验收标准
- 输出可执行计划

在闪记项目中，尤其适合这些场景：

- 新模块立项，如“多设备登录管理”“隐藏笔记恢复流程”“账号删除冷静期”
- 跨端能力设计，如 Web、Android、iOS 统一的消息发送体验
- 涉及多模块联动的变更，如认证、同步、文件上传、收藏、搜索同时受影响

不适合：

- 直接负责代码落地
- 细碎 bug 的快速修复

---

### 2.2 Atlas

`Atlas` 是执行总控，负责读取计划、拆任务、组织执行和验证。

适合做的事：

- 按计划分阶段推进
- 协调多个子任务
- 管理 todo 和中间结论
- 推动计划从“文档”变成“交付结果”

在闪记项目中，尤其适合这些场景：

- 一次性推进“账号体系”完整能力
- 按计划拆解“聊天页多媒体消息能力”
- 从架构文档出发，逐步落地后端模块、客户端模块和接口联调

不适合：

- 在需求还模糊时强行开工
- 处理单个特别深的技术难题

---

### 2.3 Sisyphus

`Sisyphus` 是默认主力总控，适合“我知道大概要做什么，但不想自己精细拆步骤”时使用。

适合做的事：

- 中等复杂度需求直接推进
- 自动调用辅助角色完成资料搜索、代码探索、实现和验证
- 需要“别停下来，持续往前做”的任务

在闪记项目中，尤其适合这些场景：

- 给现有 API 增补一组接口
- 为 Android 端接入一段已有的接口流程
- 实现某个页面或模块的完整闭环
- 从已有文档出发做一段连续开发工作

不适合：

- 大型需求前期的严谨澄清
- 需要 GPT/Codex 风格深度推理的问题攻坚

---

### 2.4 Hephaestus

`Hephaestus` 是深度单兵，适合“这里有个难点，需要一个代理自己钻进去解决到底”。

适合做的事：

- 复杂 bug 排查
- 跨模块调用链梳理
- 大范围重构
- 底层机制研究
- 高强度推理和端到端修复

在闪记项目中，尤其适合这些场景：

- Token 刷新失败或多设备登录状态错乱
- Android 离线同步冲突问题
- 上传链路、缩略图生成、消息记录之间的数据一致性问题
- Web / Android / iOS 三端行为不一致时的根因分析

不适合：

- 替代项目级统筹
- 做需求访谈和前期规划

---

### 2.5 Oracle

`Oracle` 是架构与疑难咨询角色。

适合做的事：

- 技术选型
- 模块边界判断
- 一致性、性能、安全取舍
- 长期可维护性评估

在闪记项目中的典型问题：

- Token 刷新和多设备登录，状态应该如何建模
- 聊天消息、收藏、搜索索引之间应该如何保持一致
- 文件上传和缩略图处理是同步还是异步
- 客户端离线数据同步应使用什么冲突策略

---

### 2.6 Librarian

`Librarian` 是外部资料与文档搜索角色。

适合做的事：

- 查第三方库文档
- 查框架最佳实践
- 查官方接口规范
- 查外部开源实现参考

在闪记项目中的典型用途：

- 查 Jetpack Compose、SwiftUI、Room、CoreData、Spring Boot、MyBatis-Plus 的最佳实践
- 查 MinIO 上传、JWT 刷新、邮件验证码、Elasticsearch 检索方案

---

### 2.7 Explore

`Explore` 是项目内快速代码和模式搜索角色。

适合做的事：

- 快速扫目录结构
- 定位入口文件
- 查调用链
- 搜索已有模式

在闪记项目中的典型用途：

- 快速找认证模块、消息模块、同步模块代码入口
- 查已有错误处理、分页响应、DTO 命名模式
- 查三端是否已有统一设计规范实现

## 三、我在这个项目中的默认调用规则

### 3.1 需求刚出现，还没想清楚

先用 `Prometheus`。

判断标准：

- 我说不清影响哪些模块
- 我不确定边界和验收标准
- 我担心做着做着范围失控

适合的 prompt：

```text
@plan 为闪记新增“多设备登录管理”能力。请基于现有需求、架构和 API 文档，先帮我澄清范围、边界、风险、数据模型、接口改动和验收标准。
```

---

### 3.2 需求已经明确，要系统推进

先有计划，再用 `Atlas`。

判断标准：

- 已经有计划文档
- 任务跨模块，无法一次改完
- 我希望按阶段推进并保留过程

适合的入口：

```text
/start-work
```

适用任务：

- 账号体系完整落地
- 聊天消息模块从文字扩展到图片、语音、视频、文件
- 收藏、搜索、统计、隐藏机制的成套交付

---

### 3.3 需求比较明确，但我不想自己拆步骤

直接用 `Sisyphus`。

判断标准：

- 我知道目标
- 但不想自己手工拆任务
- 也不一定需要正式计划

适合的 prompt：

```text
ulw

为闪记项目实现“闪记置顶”能力，要求补充后端接口、Web 列表页交互、必要的数据结构和基本验证。请先探索现有代码与文档，再端到端完成。
```

适用任务：

- 单个中型功能的闭环实现
- 某个页面加一个新能力
- 某个模块补接口和前端联动

---

### 3.4 出现复杂技术难题

切 `Hephaestus`。

判断标准：

- 问题有明显技术深度
- 涉及多个模块、多个文件
- 需要深入研究根因，而不是快速试错

适合的 prompt：

```text
切换到 Hephaestus。
请深挖闪记项目的 Token 自动刷新机制，重点排查以下问题：
1. Access Token 过期后重试是否可能形成并发刷新
2. 多设备登录时旧 Token 是否会被错误踢出
3. Web 与 Android 的刷新时序是否会出现不一致

请先梳理调用链和状态模型，再给出根因与修复。
```

适用任务：

- Token / Session / 同步 / 上传链路问题
- 复杂性能问题
- 大型重构前的机制梳理

---

### 3.5 我需要判断方案，而不是马上写代码

找 `Oracle`。

适合的 prompt：

```text
让 Oracle 评估闪记项目的多设备登录设计：
Refresh Token 应该按设备维度维护，还是按用户维度维护？
请从安全性、实现复杂度、客户端体验和后续维护成本四个维度给出建议。
```

---

### 3.6 我需要外部资料和官方最佳实践

找 `Librarian`。

适合的 prompt：

```text
让 Librarian 查一下：
1. Spring Boot 3 + JWT 刷新令牌最佳实践
2. Android Room 增量同步常见做法
3. SwiftUI 列表消息页的性能注意事项
请结合闪记项目说明哪些做法值得采用。
```

---

### 3.7 我需要快速理解当前仓库现状

找 `Explore`。

适合的 prompt：

```text
让 Explore 快速梳理闪记项目当前与“消息记录模块”相关的代码入口、目录、DTO、API 调用链和持久化位置。
```

## 四、项目阶段对应角色

| 项目阶段 | 主角色 | 辅助角色 | 说明 |
|----------|--------|----------|------|
| 需求澄清 | Prometheus | Oracle, Librarian | 先定义范围和验收 |

## 五、针对闪记项目的推荐用法

### 5.1 我最常用的主路径

如果是较大的功能，默认使用：

1. `Prometheus` 产计划
2. `Atlas` 负责执行
3. 执行中遇到技术难点，切 `Hephaestus`
4. 需要架构判断时调用 `Oracle`
5. 需要外部文档时调用 `Librarian`

### 5.2 我最省事的主路径

如果是中等复杂任务，默认使用：

1. 直接 `Sisyphus` 或 `ulw`
2. 让它自己探索、实现、验证
3. 遇到攻坚问题再切 `Hephaestus`

### 5.3 小任务不要过度编排

以下场景不必走完整流程：

- 文案修正
- 单接口字段补充
- 单页面样式微调
- 小范围表单校验修改
- 单端小 bug 修复

这些任务直接让当前代理或 `Sisyphus` 处理即可。

## 六、完整项目演进示例

下面用一个贴近闪记项目的例子说明。

### 场景

目标：实现“多设备登录管理 + Token 自动刷新 + 设备管理页”。

这件事会同时影响：

- 需求边界
- 后端认证模块
- 用户模块
- Web 个人中心
- Android / iOS 登录态管理
- 接口设计
- 安全策略

因此不适合一上来直接写代码。

### 第一步：Prometheus 先做规划

我会这样调用：

```text
@plan 为闪记项目实现“多设备登录管理 + Token 自动刷新 + 设备管理页”。
请基于现有需求分析、架构设计、客户端架构设计和 API 接口设计文档：
1. 明确范围和不做范围
2. 列出涉及模块
3. 补充数据模型和接口变更
4. 给出客户端状态流转
5. 给出验收标准和回滚点
```

此时我要的不是代码，而是：

- 服务端应该新增哪些表和字段
- Token 与设备的关系如何建模
- Web / Android / iOS 各要改什么
- 验收标准如何定义

### 第二步：Atlas 按计划开工

当计划确认后，交给 `Atlas`：

```text
/start-work
```

此时 Atlas 适合做：

- 先实现后端 Refresh Token 和设备表
- 再补设备列表、远程登出接口
- 再推进 Web 端设备管理页
- 最后推进 Android / iOS 登录态适配
- 每一步都做验证

### 第三步：遇到认证疑难问题，切 Hephaestus

如果执行过程中出现问题，例如：

- 刷新接口偶发 401
- 多设备之间互相挤掉登录态
- Android 本地缓存与服务端设备状态不一致

这时切 `Hephaestus`：

```text
切换到 Hephaestus。
请系统排查闪记项目多设备登录中的登录态错乱问题，重点覆盖：
1. Refresh Token 轮换
2. 并发刷新
3. 设备撤销后的客户端状态同步
4. Web / Android / iOS 三端一致性
请先分析根因，再实施修复并给出验证方法。
```

### 第四步：架构争议交给 Oracle

如果我不确定：

- Refresh Token 是否应该存 Redis
- 设备数上限如何控制
- 单设备登录模式如何兼容现有设计

这时候问 `Oracle`：

```text
让 Oracle 评估闪记项目多设备登录的服务端状态设计：
是 MySQL 持久化为主，还是 Redis 为主？
请说明两种方案的复杂度、可靠性、扩展性和运维成本。
```

### 第五步：查外部实践交给 Librarian

如果我要确认最佳实践：

```text
让 Librarian 调研：
1. 主流 App 的多设备登录管理实践
2. JWT + Refresh Token 的设备维度管理
3. Android / iOS 登录态持久化最佳实践
请结合闪记项目给出可落地建议。
```

### 第六步：小收尾用 Sisyphus

等主链路打通后，剩余一些补丁任务：

- 登录页增加设备提醒
- 设备管理页文案优化
- 补一个接口字段
- 调整错误提示

这些就不需要再开完整编排，可以直接交给 `Sisyphus`：

```text
请为闪记项目补齐设备管理页的细节体验：
1. 设备列表增加“当前设备”标识
2. 远程登出后给出明确提示
3. Token 过期跳转登录页前保留上下文提示
4. 补充必要的前端校验和接口错误处理
```

## 七、我自己的最终使用准则

为了避免每次都纠结，我在闪记项目里直接遵循下面的准则：

1. 新功能较大或跨模块，先 `Prometheus`
2. 计划明确后，用 `Atlas`
3. 中型任务直接做，用 `Sisyphus`
4. 技术难题或复杂 bug，用 `Hephaestus`
5. 架构拿不准，问 `Oracle`
6. 查资料用 `Librarian`
7. 查仓库现状用 `Explore`
8. 小任务不搞复杂流程，直接做

---

## 八、最适合当前项目的简化工作流

### 工作流 A：大需求

```text
Prometheus -> Atlas -> Hephaestus（按需）-> Sisyphus 收尾
```

适合：

- 账号体系
- 同步系统
- 搜索系统
- 多媒体消息能力

### 工作流 B：中型功能

```text
Sisyphus -> Hephaestus（遇难题时）
```

适合：

- 置顶、隐藏、恢复、收藏等单模块功能
- 某一个页面和一组接口的联动

### 工作流 C：难题攻坚

```text
Explore -> Hephaestus -> Oracle（需要决策时）
```

适合：

- 复杂 bug
- 数据一致性问题
- 架构性缺陷修复

---

## 九、结论

对当前闪记项目来说，不需要把所有角色都频繁手动切来切去。最有效的方式是：

- 大需求：`Prometheus` + `Atlas`
- 中型任务：`Sisyphus`
- 攻坚问题：`Hephaestus`
- 架构判断：`Oracle`
- 资料搜索：`Librarian`
- 仓库摸底：`Explore`

只要我按这个节奏用，代理体系就会从“很多名字”变成“清晰的项目推进工具链”。
